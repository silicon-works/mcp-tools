# Integration Scenarios: ssh
# Required: HTB VPN connection, target box with SSH access (password or key)
# Recommended FIRST box: DevVortex (easy Linux, SSH + web, exercises password
#   auth, key auth after foothold, run_script for privesc enum, background for
#   persistence, copy_to for payload upload, and tunnel-through-localhost patterns)
# Also good: Surveillance (medium, SSH key from web exploit, ed25519 key format,
#   PubkeyAcceptedAlgorithms needed, good for key auth + privesc chain)
# Prerequisites: Valid SSH credentials (username + password or key), target reachable on VPN
# Run with: pytest tests/tools/test_ssh.py -m integration --tool=ssh \
#           --target=<IP> --username=<USER> --password=<PASS> -v
#
# Data source: Trajectory analysis of 1445 SSH method calls across 22 HTB engagements.
#   Method calls: exec=1125, run_script=111, shell=53, copy_to=36, background=23,
#   copy_from=9, upload_binary=1
#   Success rates: exec=65%, run_script=83%, shell=74%, copy_to=72%,
#   background=65%, copy_from=67%, upload_binary=100%
#   Key auth: 257 calls used key parameter (18% of total), all with ed25519 keys
#   Non-standard ports: 127.0.0.1:60431, :55517, :38229, :37619, :52817 (tunnel/pivot)
#   Error data: 88 "Not connected" (MCP transport), 47 "Tool known broken" (circuit
#   breaker), 15 "Connection closed" (MCP -32000), 174/278 exec failures (63%) are
#   remote command failures (exit 1/2) misclassified as SSH errors
#
# *** KNOWN BUG: _classify_ssh_error receives unfiltered stderr (line 634 passes
#   `errors` instead of `errors_filtered`). Commands returning non-zero exit codes
#   get classified as SSH errors because "Permanently added" warning is in stderr.
#   Exit codes 1, 2, 127 from SSH mean the REMOTE COMMAND failed, not SSH itself.
#   Only exit code 255 indicates an SSH connection/auth failure. ***

## Scenario 1: Basic command execution (password auth)
Method: exec
Args: {host: <IP>, username: <USER>, password: <PASS>, command: "id"}
Expected: success=true, stdout contains "uid=", exit_code=0
Notes: The single most common SSH call (66 calls for just "id" alone). Verifies
  connectivity, authentication, and basic output capture. Should complete in <5s.

## Scenario 2: Execute with custom port
Method: exec
Args: {host: <IP>, username: <USER>, password: <PASS>, command: "whoami", port: 2222}
Expected: success=true, stdout contains the username
Notes: Tests non-default SSH port. Common on HTB (e.g., port 2222). Real engagement
  data shows ports 55517, 60431, 38229, 37619, 52817, 34157, 46205 used for SSH
  tunnels/pivots (all high ephemeral ports from local port forwarding).

## Scenario 3: Multi-word command with pipes and redirection

Args: {host: <IP>, username: <USER>, password: <PASS>, command: "cat /etc/passwd | grep -v nologin | head -10"}
Expected: success=true, stdout contains "root:x:0:0:"
Notes: Tests shell metacharacter handling through SSH. Real engagement uses complex
  piped commands like "find / -group operator 2>/dev/null" and "ps auxeww 2>/dev/null".

## Scenario 4: Command with environment variable expansion
Method: exec
Args: {host: <IP>, username: <USER>, password: <PASS>, command: "echo $PATH && echo $HOME && echo $USER"}
Expected: success=true, stdout contains path entries and username
Notes: Validates that remote shell expands environment variables correctly.

## Scenario 5: Command returning non-zero exit code (NOT an SSH error)
Method: exec
Args: {host: <IP>, username: <USER>, password: <PASS>, command: "cat /etc/shadow"}
Expected: success=false, exit_code=1, error should indicate COMMAND failure not SSH failure
Notes: CRITICAL test. As a non-root user, this returns exit code 1 ("Permission denied"
  from cat, NOT from SSH). The current code (line 634) passes unfiltered stderr to
  _classify_ssh_error, which misclassifies this as an SSH auth error. 126 of 278
  failures in engagement data were exit_code=1 misclassified this way. The error_class
  should be "command" or similar, NOT "auth". The "Warning: Permanently added" line
  should NOT appear in the error message.

## Scenario 6: Command not found (exit code 127)
Method: exec
Args: {host: <IP>, username: <USER>, password: <PASS>, command: "nonexistent_command_xyz"}
Expected: success=false, exit_code=127, error indicates command not found
Notes: Tests exit code 127 handling. Real data shows this for missing tools (e.g.,
  python3 not installed, ldapsearch not available). Should NOT be classified as SSH error.

## Scenario 7: Command returning exit code 2 (misuse)
Method: exec
Args: {host: <IP>, username: <USER>, password: <PASS>, command: "grep --invalid-option /etc/passwd"}
Expected: success=false, exit_code=2
Notes: Exit code 2 = command misuse. 48 occurrences in engagement data. Should be
  distinguished from SSH errors. Currently falls through to generic "SSH error (exit
  code 2)" with the Permanently added warning leaked into the message.

## Scenario 8: Long output command

Expected: success=true, stdout contains many lines of output

## Scenario 11: SSH key authentication with ed25519 (OpenSSH format)
Method: exec
Args: {host: <IP>, username: <USER>, key: "-----BEGIN OPENSSH PRIVATE KEY-----\n<key_content>\n-----END OPENSSH PRIVATE KEY-----", command: "id", ssh_options: "-o PubkeyAcceptedAlgorithms=+ssh-ed25519"}
Expected: success=true, stdout contains "uid="
Notes: THE critical key auth test. All 257 key-auth calls in engagement data used
  ed25519 keys in OpenSSH format. The server converts to PEM via _convert_openssh_to_pem().
  Without "-o PubkeyAcceptedAlgorithms=+ssh-ed25519", the container's OpenSSH client
  may reject the key with "error in libcrypto" (9 occurrences in data). The agent
  learned this fix after initial failures and applied it in all subsequent calls
  (50 calls with this option).

## Scenario 12: Ed25519 key WITHOUT PubkeyAcceptedAlgorithms (expected failure)
Method: exec
Args: {host: <IP>, username: <USER>, key: "-----BEGIN OPENSSH PRIVATE KEY-----\n<ed25519_key>\n-----END OPENSSH PRIVATE KEY-----", command: "id"}
Expected: success=false, error contains "error in libcrypto" or "Permission denied"
Notes: Validates the failure mode that led to the PubkeyAcceptedAlgorithms workaround.
  The OpenSSH client in the Kali container may not negotiate ed25519 by default against
  older sshd versions. The error message should suggest adding
  "-o PubkeyAcceptedAlgorithms=+ssh-ed25519" to ssh_options.

## Scenario 13: RSA key authentication (PEM format, no conversion needed)
Method: exec
Args: {host: <IP>, username: <USER>, key: "-----BEGIN RSA PRIVATE KEY-----\n<key_content>\n-----END RSA PRIVATE KEY-----", command: "id"}
Expected: success=true, stdout contains "uid="
Notes: Tests PEM RSA key that should NOT trigger conversion. The _convert_openssh_to_pem
  method should detect "BEGIN RSA PRIVATE KEY" and return as-is.

## Scenario 14: ECDSA key authentication
Method: exec
Args: {host: <IP>, username: <USER>, key: "-----BEGIN EC PRIVATE KEY-----\n<key_content>\n-----END EC PRIVATE KEY-----", command: "id"}
Expected: success=true, stdout contains "uid="
Notes: Tests EC key format. _convert_openssh_to_pem should detect "BEGIN EC PRIVATE KEY"
  and skip conversion.

## Scenario 15: SSH key with passphrase (graceful failure)
Method: exec
Args: {host: <IP>, username: <USER>, key: "-----BEGIN OPENSSH PRIVATE KEY-----\n<encrypted_key>\n-----END OPENSSH PRIVATE KEY-----", command: "id"}
Expected: success=false, error_class="auth"
Notes: Encrypted keys cannot be used (no interactive passphrase prompt in BatchMode).
  _convert_openssh_to_pem will fail with "Key conversion failed" when ssh-keygen asks
  for passphrase with -P "". The error should suggest decrypting the key first.

## Scenario 16: Key auth to localhost through SSH tunnel (pivot pattern)
Method: exec
Args: {host: "127.0.0.1", username: <USER>, key: "<KEY>", command: "id", port: 55517, ssh_options: "-o PubkeyAcceptedAlgorithms=+ssh-ed25519"}
Expected: success=true, stdout contains "uid="
Notes: Real engagement pattern. After establishing an SSH tunnel (e.g., -L 55517:target:22),
  the agent connects to 127.0.0.1 on the forwarded port. Ports 55517, 60431, 38229,
  37619, 52817, 34157, 46205 all appear in engagement data for this pattern.

## Scenario 17: Key with trailing newline variations
Method: exec
Args: {host: <IP>, username: <USER>, key: "<KEY_WITH_EXTRA_NEWLINES>", command: "id", ssh_options: "-o PubkeyAcceptedAlgorithms=+ssh-ed25519"}
Expected: success=true
Notes: Keys extracted from web apps or databases may have extra whitespace/newlines.
  The key is written to a temp file, so leading/trailing whitespace should be handled.

## Scenario 22: Shell with command that returns non-zero (chain breakage)
Method: shell
Args: {host: <IP>, username: <USER>, password: <PASS>, commands: ["echo 'step1'", "false", "echo 'step3'"]}
Expected: success=false (due to && joining), stdout contains "step1" but NOT "step3"
Notes: Tests the && chain behavior. Since "false" returns exit code 1, "step3" should
  never execute. This is a design choice - if you need all commands to run regardless,
  use exec with ";" instead of shell.

## Scenario 38: Upload large binary (chunking test)
