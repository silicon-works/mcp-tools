# Integration Scenarios: bloodhound
# Required HTB Machine: Windows AD (e.g., Garfield, DarkZero, Pirate, Certified, Hercules, Vintage)
# Prerequisites: Valid AD credentials (username + password), DC IP reachable on VPN
# Run with: pytest tests/tools/test_bloodhound.py -m integration --tool=bloodhound \
#           --target=<DC_IP> --domain=<DOMAIN> --username=<USER> --password=<PASS> -v

# ═══════════════════════════════════════════════════════════════════════════════
# FULL DOMAIN COLLECTION SCENARIOS (all collection presets and individual modes)
# ═══════════════════════════════════════════════════════════════════════════════

## Scenario 1: Default collection (Group, LocalAdmin, Session, Trusts)
Method: collect
Args: {domain: <DOMAIN>, username: <USER>, password: <PASS>, dc_ip: <DC_IP>, collection: "Default", timeout: 120}
Expected: success=true, file_count>=4, collection_types includes "users" and "groups"
Notes: Safe balanced collection. Produces 4-7 JSON files. Good first test to confirm
       connectivity and authentication work.
Machines: Garfield (garfield.htb), Certified (certified.htb), DarkZero (darkzero.htb)

## Scenario 2: All collection (everything except LoggedOn)
Method: collect
Args: {domain: <DOMAIN>, username: <USER>, password: <PASS>, dc_ip: <DC_IP>, collection: "All", timeout: 300}
Expected: success=true, file_count>=7, collection_types includes "users", "groups",
          "computers", "domains", "gpos", "ous", "containers"
Notes: Most comprehensive. 7 output files for a typical domain. May take 1-5 minutes
       depending on domain size. Uses SMB/RPC to enumerate each computer.
Machines: Garfield (garfield.htb -- small domain, <10 computers)
Evidence: [Garfield ses_295cc59d] All+zip collection took 91-153s with j.arbuckle creds.
          [Hercules ses_2f27548b] All collection took 16s (small domain).

## Scenario 3: Group-only collection
Method: collect
Args: {domain: <DOMAIN>, username: <USER>, password: <PASS>, dc_ip: <DC_IP>, collection: "Group", timeout: 60}
Expected: success=true, collection_types includes "groups" and "users"
Notes: LDAP-only, fast. Useful for targeted group membership enumeration.

## Scenario 4: ACL collection
Method: collect
Args: {domain: <DOMAIN>, username: <USER>, password: <PASS>, dc_ip: <DC_IP>, collection: "ACL", timeout: 120}
Expected: success=true, collection_types includes "users" (ACL data embedded in user/computer objects)
Notes: LDAP-only. Essential for finding WriteDACL, GenericAll, ForceChangePassword edges.

## Scenario 5: Session collection
Method: collect
Args: {domain: <DOMAIN>, username: <USER>, password: <PASS>, dc_ip: <DC_IP>, collection: "Session", timeout: 120}
Expected: success=true, collection_types includes "computers"
Notes: Enumerates active sessions on each computer via SMB (NetSessionEnum).
       Requires network access to each computer. Noisy -- generates SMB connections to
       every computer in the domain. Data shows which users are logged into which machines.
Machines: Garfield (garfield.htb -- small domain, fast enumeration)

## Scenario 6: ObjectProps collection
Method: collect
Args: {domain: <DOMAIN>, username: <USER>, password: <PASS>, dc_ip: <DC_IP>, collection: "ObjectProps", timeout: 120}
Expected: success=true, collection_types includes "users" and "computers"
Notes: LDAP-only. Collects object properties like lastLogon, servicePrincipalName,
       msDS-AllowedToDelegateTo, adminCount, description, etc. Critical for identifying
       delegation paths, Kerberoastable accounts, and admin-tier users.

## Scenario 7: Trusts collection
Method: collect
Args: {domain: <DOMAIN>, username: <USER>, password: <PASS>, dc_ip: <DC_IP>, collection: "Trusts", timeout: 60}
Expected: success=true, collection_types includes data with trust relationships
Notes: Fast, targeted collection. LDAP-only. Shows inter-domain and inter-forest
       trust relationships, trust direction, and trust type (external, forest, etc.).
Machines: DarkZero (darkzero.htb -- has forest trust to darkzero.ext)

## Scenario 8: Container collection

## Scenario 12: LoggedOn collection (requires admin)
Method: collect
Args: {domain: <DOMAIN>, username: <ADMIN_USER>, password: <ADMIN_PASS>, dc_ip: <DC_IP>, collection: "LoggedOn", timeout: 180}
Expected: success=true if user has local admin on target computers
Notes: Uses Win32 API (NetWkstaUserEnum) to enumerate all logged-on users.
       Requires local admin rights on each computer -- will silently skip computers
       where the user lacks admin. Excluded from "All" preset due to noise and
       privilege requirements. More thorough than Session but requires admin.
Machines: Any box where you have local admin creds (e.g., post-exploitation)

## Scenario 13: LoggedOn as non-admin (expected partial failure)
Method: collect
Args: {domain: <DOMAIN>, username: <USER>, password: <PASS>, dc_ip: <DC_IP>, collection: "LoggedOn", timeout: 120}
Expected: success=true but with minimal data (most computers silently skipped)
Notes: LoggedOn requires admin rights per-computer. With a regular domain user,
       most computer enumerations will return empty results. The collection still
       "succeeds" (produces output files) but with sparse data.

## Scenario 20: NTLM password auth (explicit)
Method: collect_stealth
Args: {domain: <DOMAIN>, username: <USER>, password: <PASS>, dc_ip: <DC_IP>, auth_method: "ntlm", timeout: 120}
Expected: success=true
Notes: Forces NTLM auth even if Kerberos is available. Useful when Kerberos is
       misconfigured or clock is skewed. Bypasses KDC entirely.
Evidence: [Pirate ses_34164f11] auth_method=ntlm with ms01$ took 69-70s, reliable.

## Scenario 21: Pass-the-hash (NTLM hash)
Method: collect_stealth
Args: {domain: <DOMAIN>, username: <USER>, hashes: "<LM:NT>", dc_ip: <DC_IP>, auth_method: "ntlm", timeout: 120}
Expected: success=true
Notes: Uses extracted NTLM hash instead of plaintext password. LM hash is usually
       aad3b435b51404ee (empty) for modern AD. The NT hash is the actual credential.
Evidence: [Pirate ses_34164f11] ms01$ with hashes="aad3b435b51404ee:b80b20b63597d94d..."
          took 11s (call 2) and 7s (call 13, with dc_host). Fastest auth method observed.
          [Pirate ses_341ab810] ms01$ with hashes took 11s -- consistent.
Machines: Pirate (pirate.htb -- ms01$ machine account hash from gMSA extraction)

## Scenario 22: Machine account authentication
Method: collect_stealth
Args: {domain: <DOMAIN>, username: "MACHINE$", password: "<MACHINE_PASS>", dc_ip: <DC_IP>, auth_method: "ntlm", timeout: 120}
Expected: success=true (machine accounts can authenticate and read AD)
Notes: Machine accounts (trailing $) are valid LDAP bind credentials.
       Observed in Pirate.htb engagement with ms01$ account.
Evidence: [Pirate ses_34164f11] ms01$ used across 13 calls, all successful.
          Tried with password, hashes, kerberos, and NTLM -- all worked.
Machines: Pirate (pirate.htb -- ms01$ machine account)

## Scenario 23: AES key authentication
Method: collect_stealth
Args: {domain: <DOMAIN>, username: <USER>, aes_key: "<256_BIT_HEX>", dc_ip: <DC_IP>, dc_host: "dc01.<DOMAIN>", timeout: 120}
Expected: success=true if AES key is valid for the principal
Notes: AES-256 keys are 64 hex chars. Extracted from keytabs, secretsdump,
       or Kerberos ticket analysis. Does not require password or NT hash.
       dc_host is recommended since AES auth uses Kerberos which needs DC hostname.
       Avoids transmitting any password-derived material.
Machines: Any box after secretsdump (AES keys in output)

## Scenario 24: Kerberos auth with ccache from impacket getTGT
Method: collect_stealth
Args: {domain: <DOMAIN>, username: <USER>, kerberos: true, ccache_path: "/session/credentials/<USER>.ccache", dc_ip: <DC_IP>, dc_host: "dc01.<DOMAIN>", timeout: 120}
Expected: success=true if ccache is valid and clock skew is within 5 minutes
Prerequisite: Run impacket.get_tgt first to create the ccache file at

Notes: Full cross-tool chain: impacket creates ccache -> bloodhound consumes it.
       dc_host is often needed with Kerberos since DNS auto-discovery may not resolve
       the DC hostname correctly from inside the container.
Evidence: [Certified ses_2ce83665] judith.mader.ccache from impacket getTGT, kerberos=true,
          collect_stealth took 80-137s. Master agent ran this directly (not sub-agent).
Machines: Certified (certified.htb), Pirate (pirate.htb -- tested with ms01$)

## Scenario 25: Kerberos auth with ccache from certipy authenticate
Method: collect_stealth
Args: {domain: <DOMAIN>, username: <USER>, kerberos: true, ccache_path: "/session/credentials/<USER>.ccache", dc_ip: <DC_IP>, dc_host: "dc01.<DOMAIN>", timeout: 120}
Expected: success=true if ccache is valid
Prerequisite: Run certipy.authenticate with a PFX certificate to get a ccache:
              certipy auth -pfx user.pfx -dc-ip <DC_IP> -> <USER>.ccache
Notes: Cross-tool chain: certipy authenticate (PKINIT) -> ccache -> bloodhound.
       Common in ADCS attack paths (ESC1-ESC8) where you get a certificate,
       authenticate with it to get a TGT, then use that TGT for bloodhound collection.
Machines: Certified (certified.htb -- has vulnerable ADCS)

## Scenario 26: Kerberos auth with password (Kerberos pre-auth)
Method: collect_stealth
Args: {domain: <DOMAIN>, username: <USER>, password: <PASS>, dc_ip: <DC_IP>, auth_method: "kerberos", dc_host: "dc01.<DOMAIN>", timeout: 120}
Expected: success=true if Kerberos is available and clock is synced
Notes: Forces Kerberos auth using password for pre-authentication (AS-REQ).
       If clock skew >5min, will fail with KRB_AP_ERR_SKEW -- use clock_offset
       meta-parameter to compensate.
Evidence: [Pirate ses_34164f11] ms01$ with auth_method=kerberos took 67-68s. Agent
          iterated through auth methods: auto, kerberos, ntlm, kerberos+dc_host.
          [Hercules ses_2f27548b] ken.w with kerberos=true (All collection) took 41s.

## Scenario 27: Kerberos flag (kerberos=true) with password
Method: collect_stealth
Args: {domain: <DOMAIN>, username: <USER>, password: <PASS>, dc_ip: <DC_IP>, kerberos: true, timeout: 120}
Expected: success=true (kerberos=true + password triggers Kerberos pre-auth)
Notes: Subtly different from auth_method="kerberos". The kerberos=true flag adds -k
       to the CLI (ccache-based auth hint), while auth_method="kerberos" adds
       --auth-method kerberos. When password is also provided, both paths work:
       the tool does Kerberos pre-auth with the password.
Evidence: [Pirate ses_34164f11] ms01$ with kerberos=true took 72s (call 9).
          [Pirate ses_341ab810] ms01$ with kerberos=true took 6s (call 1, second session).

# ═══════════════════════════════════════════════════════════════════════════════
# CLOCK SKEW AND FAKETIME (Kerberos clock synchronization)
# ═══════════════════════════════════════════════════════════════════════════════

## Scenario 28: Positive clock offset (DC ahead of container)
Method: collect_stealth
Args: {domain: <DOMAIN>, username: <USER>, password: <PASS>, dc_ip: <DC_IP>, auth_method: "kerberos", clock_offset: "+2h", dc_host: "dc01.<DOMAIN>", timeout: 120}
Expected: success=true (FAKETIME shifts container clock forward to match DC)
Notes: The clock_offset meta-parameter is intercepted by BaseMCPServer and injected
       via LD_PRELOAD=libfaketime.so. The actual bloodhound-python process sees a
       shifted system clock. Format: "+Nh" or "-Nh" (hours), "+Nm" or "-Nm" (minutes).
       Use when DC's clock is ahead of the container.

## Scenario 29: Negative clock offset (DC behind container)
Method: collect_stealth
Args: {domain: <DOMAIN>, username: <USER>, password: <PASS>, dc_ip: <DC_IP>, auth_method: "kerberos", clock_offset: "-30m", dc_host: "dc01.<DOMAIN>", timeout: 120}
Expected: success=true (FAKETIME shifts container clock backward)
Notes: Less common scenario -- DC's clock is behind the container. HTB DCs are usually
       within a few seconds but network-introduced delays or VM clock drift can cause this.

## Scenario 30: Clock skew too large (deliberate failure)
Method: collect_stealth
Args: {domain: <DOMAIN>, username: <USER>, password: <PASS>, dc_ip: <DC_IP>, auth_method: "kerberos", clock_offset: "-6h", timeout: 60}
Expected: success=false, error_class="config", retryable=true, suggestions mention clock
Notes: 6-hour offset exceeds Kerberos 5-minute window. Tests both FAKETIME and error
       classification. The clock_offset meta-parameter is stripped by BaseMCPServer
       and injected via libfaketime.

## Scenario 31: Clock offset with All collection (not just stealth)
Method: collect
Args: {domain: <DOMAIN>, username: <USER>, password: <PASS>, dc_ip: <DC_IP>, collection: "All", auth_method: "kerberos", clock_offset: "+1h", dc_host: "dc01.<DOMAIN>", timeout: 300}
Expected: success=true (FAKETIME works for full collection too, not just DCOnly)
Notes: Verify FAKETIME applies correctly to the full collection pipeline including
       SMB/RPC computer enumeration, not just the LDAP phase.

## Scenario 38: LDAPS collection
Method: collect_stealth
Args: {domain: <DOMAIN>, username: <USER>, password: <PASS>, dc_ip: <DC_IP>, use_ldaps: true, timeout: 120}
Expected: success=true if DC has LDAPS on port 636; network error otherwise
Notes: Encrypts all LDAP traffic. Not all HTB boxes have LDAPS configured.

## Scenario 39: LDAPS with channel binding
Method: collect_stealth
Args: {domain: <DOMAIN>, username: <USER>, password: <PASS>, dc_ip: <DC_IP>, use_ldaps: true, ldap_channel_binding: true, timeout: 120}
Expected: success=true if DC enforces EPA; may fail if DC doesn't support channel binding
Notes: EPA (Extended Protection for Authentication) is increasingly common.
       This flag forces LDAPS + channel binding together. bloodhound-python 1.9
       supports this. Required on DCs with "Require" EPA policy.

## Scenario 40: LDAPS without channel binding on EPA-enforcing DC (expected failure)
Method: collect_stealth
Args: {domain: <DOMAIN>, username: <USER>, password: <PASS>, dc_ip: <DC_IP>, use_ldaps: true, ldap_channel_binding: false, timeout: 60}
Expected: success=false if DC enforces EPA, error_class="auth"
Notes: When a DC enforces EPA, LDAPS without channel binding will fail with an auth
       error. The error classification should suggest enabling ldap_channel_binding.
       If the DC does NOT enforce EPA, this will succeed normally.

## Scenario 41: LDAPS with full All collection
Method: collect
Args: {domain: <DOMAIN>, username: <USER>, password: <PASS>, dc_ip: <DC_IP>, collection: "All", use_ldaps: true, timeout: 300}
Expected: success=true if LDAPS is available
Notes: Full collection over LDAPS. The computer enumeration (SMB/RPC) still uses
       cleartext SMB -- only the LDAP queries to the DC go over TLS. This is still
       valuable for IDS evasion since the LDAP queries contain the most identifiable
       bloodhound traffic patterns.
