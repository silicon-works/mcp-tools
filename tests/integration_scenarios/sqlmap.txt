# Integration Scenarios: sqlmap
# Required HTB Machine: Web box with SQL injection (see per-scenario recommendations)
# Recommended FIRST box: Codify (easy Linux, SQLite injection in Node.js app, tests
#   test_injection + enumerate_dbs + dump_table with SQLite backend, fast runs)
# Recommended FULL box: Jarvis (medium Linux, MySQL + UNION + stacked + os_shell + file ops)
# Prerequisites: Target reachable on VPN, injectable parameter identified or suspected
# Run with: pytest tests/tools/test_sqlmap.py -m integration --tool=sqlmap \
#           --target=<IP> -v
# NOTE: sqlmap is SLOW. Set generous timeouts (300-1800s per method).
#
# Data source: 27 sqlmap calls across 4 HTB engagements (Cobblestone, CCTV, HTB-misc x2).
#   Method calls: test_injection=6, file_write=9, file_read=2, sql_query=1,
#     os_shell=1, enumerate_dbs=1, dump_table=2, enumerate_tables=0, dump_all=0,
#     dump_passwords=0, custom_query(invalid)=1
#   Timeout rate: enumerate_dbs 100% (timeout=120 too low), os_shell 100% (MySQL
#     UDF upload slow), test_injection 33% (level=5/risk=3 slow on POST)
#   Common errors: timeout too low for POST blind injection (120-300s insufficient),
#     file_write missing required params (remote_path, local_file), file_write on
#     MySQL returns success=false even with FILE privilege (secure_file_priv),
#     os_shell timeout on MySQL (UDF upload takes >300s)
#   Coverage gaps: enumerate_tables, dump_all, dump_passwords never called in
#     engagements — agents jump straight to sql_query or dump_table
#
# Server methods (10): test_injection, enumerate_dbs, enumerate_tables, dump_table,
#   dump_all, dump_passwords, os_shell, file_read, file_write, sql_query
# Common params (all methods): url, data, cookie, headers, method, auth_type,
#   auth_cred, csrf_token, csrf_url, dbms, ignore_code, string, not_string, code,
#   text_only, titles, level, risk, technique, param, tamper, prefix, suffix,
#   union_cols, second_url, eval, time_sec, threads, delay, retries, safe_url,
#   safe_freq, null_connection, proxy, random_agent, flush_session
# DBMS support: MySQL, PostgreSQL, Oracle, Microsoft SQL Server, SQLite
# Techniques: B=Boolean, E=Error, U=Union, S=Stacked, T=Time, Q=Inline


# ===============================================================================
# TEST_INJECTION — DETECTION: GET PARAMETER
# Method: test_injection — detect SQL injection and identify DBMS, technique, params
# Key output: vulnerable (bool), injection_type, dbms, parameters[], details[]
# Engagement data: 6 calls, 33% timeout (level=5/risk=3 on POST). Level 1-2 with
#   GET params completes in <150s. POST blind at level=5 can exceed 1800s.
# ===============================================================================

## Scenario 1: Basic GET parameter injection test
Method: test_injection
Args: {url: "http://<IP>/page.php?id=1", timeout: 300}
Expected: success=true, vulnerable=true, dbms detected, injection_type present
Notes: First step in any SQLi workflow. Tests all techniques (BEUSTQ) at default
  level=1/risk=1. GET params at level 1 typically complete in 60-150s. If not
  injectable, escalate to Scenario 5 (higher level/risk) before giving up.

## Scenario 2: GET with explicit injection point marker
Method: test_injection
Args: {url: "http://<IP>/page.php?id=1*&category=news", timeout: 300}
Expected: success=true, tests only the id parameter (marked with *)
Notes: The * marker tells sqlmap exactly where to inject. Use when URL has multiple
  params but you know which one is injectable from manual testing.

## Scenario 3: GET with forced DBMS (skip detection)
Method: test_injection
Args: {url: "http://<IP>/page.php?id=1", dbms: "MySQL", timeout: 300}
Expected: success=true, faster detection (skips DBMS fingerprinting)
Notes: When DBMS is known from error messages, banners, or nmap service detection,
  specifying dbms saves 30-60s of fingerprinting time.

## Scenario 4: GET with specific parameter
Method: test_injection
Args: {url: "http://<IP>/search.php?q=test&page=1&sort=name", param: "q", timeout: 300}
Expected: success=true, only tests the q parameter
Notes: With param set, sqlmap skips testing page and sort. Faster than testing all
  parameters. Use when you have a suspected param from manual testing.

## Scenario 5: GET with elevated level and risk
Method: test_injection
Args: {url: "http://<IP>/page.php?id=1", level: 3, risk: 2, timeout: 600}
Expected: success=true, may find injection types missed at level=1
Notes: Level 2 tests cookie params. Level 3 adds User-Agent and Referer headers.
  Risk 2 adds heavy time-based payloads. Risk 3 adds OR-based (can modify data —
  avoid on production). Each level increase roughly doubles test time.

## Scenario 6: GET with all techniques restricted to boolean-only
Method: test_injection
Args: {url: "http://<IP>/page.php?id=1", technique: "B", timeout: 600}
Expected: success=true if boolean-based blind works
Notes: Restricting technique is useful when you want to confirm a specific injection
  type or when union/error-based are known to fail. Boolean-based is the most
  universal technique but the slowest for data extraction.

## Scenario 7: GET with time-based only (last resort)
Method: test_injection
Args: {url: "http://<IP>/page.php?id=1", technique: "T", time_sec: 10, timeout: 900}
Expected: success=true if target is vulnerable to time-based blind
Notes: Time-based is the ultimate fallback when all other techniques fail. Increase
  time_sec to 10-15 on high-latency targets (VPN adds 50-100ms). Very slow for
  data extraction — use only for detection, then switch to other techniques.

## Scenario 8: GET with string-based boolean detection (fast blind)
Method: test_injection
Args: {url: "http://<IP>/page.php?id=1", string: "Welcome", timeout: 300}
Expected: success=true, uses "Welcome" as TRUE response indicator
Notes: Dramatically speeds up boolean-based blind injection. The string must appear
  in TRUE responses and be absent from FALSE responses. Find it by comparing normal
  page vs page with invalid id. Engagement data: not used in 4 engagements but
  highly recommended for blind injection.

## Scenario 9: GET with HTTP status code detection
Method: test_injection
Args: {url: "http://<IP>/page.php?id=1", code: 200, timeout: 300}
Expected: success=true, uses HTTP 200 as TRUE indicator
Notes: Alternative to --string. Use when TRUE responses return 200 and FALSE return
  something else (302 redirect, 500 error). Less reliable than --string because
  intermediate pages may also return 200.

## Scenario 10: GET with text-only comparison
Method: test_injection
Args: {url: "http://<IP>/page.php?id=1", text_only: true, timeout: 300}
Expected: success=true, strips HTML tags before comparing responses
Notes: Use when pages have dynamic HTML content (timestamps, random tokens, ads)
  but the actual text content changes predictably. Reduces false positives from
  dynamic page elements.

## Scenario 11: GET with title-only comparison
Method: test_injection
Args: {url: "http://<IP>/page.php?id=1", titles: true, timeout: 300}
Expected: success=true, compares only <title> tags
Notes: Last-resort comparison method when page body is completely dynamic. Only
  works if the page title changes between TRUE and FALSE responses (e.g., "User
  Profile" vs "Error").

## Scenario 12: POST parameter injection test
Method: test_injection
Args: {url: "http://<IP>/login.php", data: "username=admin&password=test", timeout: 300}
Expected: success=true, injectable parameters identified
Notes: Tests all POST parameters. sqlmap auto-detects which param is injectable.
  login.php is the most common POST injection target on HTB boxes.

## Scenario 13: POST with specific injectable parameter
Method: test_injection
Args: {url: "http://<IP>/login.php", data: "username=admin&password=test", param: "username", timeout: 300}
Expected: success=true, tests only the username parameter
Notes: Halves test time by targeting one param. Use when you know the injectable
  param from error messages (e.g., "You have an error in your SQL syntax" after
  submitting a quote in username field).

## Scenario 14: POST with injection point marker in data
Method: test_injection
Args: {url: "http://<IP>/login.php", data: "username=admin*&password=test", timeout: 300}
Expected: success=true, only tests username (marked with *)
Notes: Alternative to param= for marking injection point directly in POST data.
  Same effect as Scenario 13 but more explicit.

## Scenario 15: POST with cookie authentication
Method: test_injection
Args: {url: "http://<IP>/dashboard.php", data: "search=test", cookie: "PHPSESSID=abc123; role=user", timeout: 300}
Expected: success=true, tests authenticated POST endpoint
Notes: Engagement data: Cobblestone used PHPSESSID cookie for all 18 calls.
  Required for post-login injection points. Get cookie value from browser or
  previous web-session tool output.

## Scenario 16: POST with forced HTTP method override
Method: test_injection
Args: {url: "http://<IP>/api/resource", data: "{\"id\": 1, \"name\": \"test\"}", method: "PUT", headers: "Content-Type: application/json", timeout: 300}
Expected: success=true, sends PUT request with JSON body
Notes: For RESTful APIs that use PUT/PATCH/DELETE. The method param forces the HTTP
  method. JSON body requires Content-Type header to be set explicitly.

## Scenario 17: Cookie injection test (level 2)
Method: test_injection
Args: {url: "http://<IP>/profile.php", cookie: "user_id=1", level: 2, timeout: 600}
Expected: success=true, cookie parameter user_id found injectable
Notes: Level 2 enables cookie testing. The cookie value "1" is the baseline — sqlmap
  modifies it to test for injection. Common in PHP apps using cookie-based auth
  where cookie value is used directly in SQL queries.

## Scenario 18: Cookie injection with multiple cookies
Method: test_injection
Args: {url: "http://<IP>/admin.php", cookie: "PHPSESSID=abc123; user_id=5; role=admin", level: 2, param: "user_id", timeout: 600}
Expected: success=true, tests only user_id cookie
Notes: param targets a specific cookie to avoid testing session cookies (which
  would invalidate the session). PHPSESSID changes break authentication if sqlmap
  modifies it during injection testing.


# ===============================================================================
# TEST_INJECTION — DETECTION: HEADER INJECTION
# At level >= 3, sqlmap tests User-Agent and Referer headers. Level 5 tests all
# custom headers. Header injection is rare but devastating when found.
# ===============================================================================

## Scenario 19: User-Agent header injection (level 3)
Method: test_injection
Args: {url: "http://<IP>/page.php?id=1", level: 3, risk: 2, timeout: 900}
Expected: success=true, may find injection in User-Agent or Referer
Notes: Level 3 is significantly slower — tests 3 additional injection surfaces
  (User-Agent, Referer, and expanded payloads). Only use after level 1-2 fails.
  Common in logging applications that INSERT User-Agent into database.

## Scenario 20: Custom header injection with explicit header
Method: test_injection
Args: {url: "http://<IP>/api/data", headers: "X-Forwarded-For: 127.0.0.1*", timeout: 300}
Expected: success=true, tests X-Forwarded-For header for injection
Notes: The * marker in header value tells sqlmap to inject there. Common injection
  point in apps that log or process X-Forwarded-For, X-Real-IP, or X-Custom-ID
  headers. Does not require level >= 3 because the injection point is explicitly
  marked.

# TEST_INJECTION — DETECTION: JSON BODY
# Modern web applications and APIs commonly use JSON request bodies. sqlmap
# supports JSON injection natively when Content-Type is set correctly.
# ===============================================================================

## Scenario 21: JSON body injection
Method: test_injection
Args: {url: "http://<IP>/api/v1/users", data: "{\"id\": 1, \"role\": \"user\"}", headers: "Content-Type: application/json", timeout: 300}
Expected: success=true, tests JSON parameters for injection
Notes: sqlmap parses JSON bodies and tests each value. Ensure Content-Type is set
  to application/json or sqlmap may not parse the body correctly.

## Scenario 22: JSON body with nested objects
Method: test_injection
Args: {url: "http://<IP>/api/v1/search", data: "{\"filter\": {\"name\": \"test\"}, \"page\": 1}", headers: "Content-Type: application/json", param: "filter.name", timeout: 300}
Expected: success=true, tests the nested name parameter
Notes: Use dot notation in param to target nested JSON fields. Without param,
  sqlmap tests all leaf values in the JSON tree.

## Scenario 23: JSON body with explicit injection marker
Method: test_injection
Args: {url: "http://<IP>/api/v1/users", data: "{\"id\": \"1*\", \"role\": \"user\"}", headers: "Content-Type: application/json", timeout: 300}
Expected: success=true, injects only in the id field
Notes: The * marker works inside JSON values too. Most reliable way to target
  specific JSON fields for injection.


# ===============================================================================
# TEST_INJECTION — WAF BYPASS (TAMPER SCRIPTS)
# Engagement data: Cobblestone WAF not detected. CCTV had no WAF. However, WAF
# bypass is critical for real-world and harder HTB boxes.
# ===============================================================================

## Scenario 24: WAF bypass with space-to-comment tamper
Method: test_injection
Args: {url: "http://<IP>/page.php?id=1", tamper: "space2comment", random_agent: true, timeout: 600}
Expected: success=true if tamper bypasses WAF
Notes: space2comment replaces spaces with /**/ — bypasses simple keyword filters.
  random_agent avoids "sqlmap" User-Agent detection (many WAFs block it outright).
  Always pair tamper with random_agent.

## Scenario 25: WAF bypass with multiple tamper scripts
Method: test_injection
Args: {url: "http://<IP>/page.php?id=1", tamper: "space2comment,between,randomcase,charencode", random_agent: true, timeout: 900}
Expected: success=true if combined tampers bypass WAF
Notes: Tamper chain applies left-to-right. Common effective combinations:
  MySQL WAF: space2comment + between + randomcase
  MSSQL WAF: space2mssqlblank + charencode + uppercase
  Generic: charencode + space2comment
  ModSecurity: modsecurityversioned + space2comment

## Scenario 26: WAF bypass with specific DBMS tamper
Method: test_injection
Args: {url: "http://<IP>/page.php?id=1", tamper: "space2mysqlblank,versionedkeywords", dbms: "MySQL", random_agent: true, timeout: 600}
Expected: success=true, MySQL-specific WAF bypass
Notes: MySQL-specific tampers: space2mysqlblank (uses MySQL-specific whitespace
  chars), versionedkeywords (wraps in /*!...*/), versionedmorekeywords. Only use
  with dbms=MySQL or they will produce invalid SQL.

## Scenario 27: WAF bypass with delay to avoid rate limiting
Method: test_injection
Args: {url: "http://<IP>/page.php?id=1", tamper: "space2comment", random_agent: true, delay: 2, threads: 1, timeout: 1800}
Expected: success=true, slow but avoids WAF rate limiting
Notes: Some WAFs ban IPs after N requests per second. delay=2 with threads=1 sends
  1 request every 2 seconds. Very slow but reliable. Use safe_url to keep session
  alive between requests.

## Scenario 28: WAF bypass with safe URL (session keepalive)
Method: test_injection
Args: {url: "http://<IP>/page.php?id=1", tamper: "space2comment", random_agent: true, safe_url: "http://<IP>/index.php", safe_freq: 5, timeout: 900}
Expected: success=true, visits safe_url every 5 requests
Notes: safe_url visits a normal page periodically to prevent session timeout and
  make traffic look more natural. Essential when WAF monitors session patterns.

## Scenario 29: WAF bypass with prefix/suffix (known SQL context)
Method: test_injection
Args: {url: "http://<IP>/page.php?id=1", prefix: "')", suffix: "-- -", tamper: "space2comment", timeout: 600}
Expected: success=true, uses known SQL context for injection
Notes: When you can determine the SQL query structure from error messages (e.g.,
  "SELECT * FROM items WHERE (id='1')"), set prefix="')" and suffix="-- -" to
  close the existing query correctly. Eliminates guesswork and speeds detection.

# TEST_INJECTION — DETECTION: DIFFERENT DB BACKENDS
# Each DBMS has specific injection characteristics. Forcing dbms speeds testing
# and enables backend-specific features (os-shell, file ops, etc.).
# ===============================================================================

## Scenario 30: MySQL detection and test
Method: test_injection
Args: {url: "http://<IP>/page.php?id=1", dbms: "MySQL", timeout: 300}
Expected: success=true, dbms contains "MySQL"
Notes: MySQL is the most common DBMS on HTB Linux boxes. Supports UNION, error-based
  (EXTRACTVALUE, UPDATEXML), boolean, time-based, stacked (if multi-statements
  enabled). FILE privilege enables file_read/file_write. UDF enables os_shell.
  Engagement data: Cobblestone=MySQL, CCTV=MySQL.

## Scenario 31: MSSQL detection and test
Method: test_injection
Args: {url: "http://<IP>/page.aspx?id=1", dbms: "Microsoft SQL Server", timeout: 300}
Expected: success=true, dbms contains "Microsoft SQL Server"
Notes: MSSQL is the most common on HTB Windows boxes. Supports stacked queries
  natively (unlike MySQL). xp_cmdshell enables OS command execution without UDF.
  Key advantage: stacked queries let you run arbitrary SQL including INSERT/UPDATE.

## Scenario 32: PostgreSQL detection and test
Method: test_injection
Args: {url: "http://<IP>/page.php?id=1", dbms: "PostgreSQL", timeout: 300}
Expected: success=true, dbms contains "PostgreSQL"
Notes: PostgreSQL supports COPY TO/FROM for file operations, PL/pgSQL for code
  execution. Error-based via CAST or GENERATE_SERIES. Common on modern Linux stacks.

## Scenario 33: SQLite detection and test
Method: test_injection
Args: {url: "http://<IP>/page.php?id=1", dbms: "SQLite", timeout: 300}
Expected: success=true, dbms contains "SQLite"
Notes: SQLite has no user authentication, no network access, limited file ops.
  No stacked queries in most configurations. UNION and boolean-based are the main
  techniques. Common in Node.js, Python Flask, and mobile-backend HTB boxes.

## Scenario 34: Oracle detection and test
Method: test_injection
Args: {url: "http://<IP>/page.jsp?id=1", dbms: "Oracle", timeout: 300}
Expected: success=true, dbms contains "Oracle"
Notes: Oracle is rare on HTB but appears in enterprise-themed boxes. Error-based
  via UTL_INADDR, CTXSYS.DRITHSX. Requires different syntax for UNION (needs
  FROM DUAL). File ops via UTL_FILE or Java stored procedures.

# HTTP auth methods and CSRF token handling.

## Scenario 35: Basic HTTP authentication
Method: test_injection
Args: {url: "http://<IP>/admin/page.php?id=1", auth_type: "Basic", auth_cred: "admin:password123", timeout: 300}
Expected: success=true, authenticates and tests injection
Notes: For endpoints behind HTTP Basic auth. auth_cred format is always user:password.
  Get credentials from earlier enumeration or default credential lists.

## Scenario 36: NTLM authentication (Windows/IIS)
Method: test_injection
Args: {url: "http://<IP>/app/page.aspx?id=1", auth_type: "NTLM", auth_cred: "DOMAIN\\user:password", timeout: 300}
Expected: success=true, NTLM authenticated injection test
Notes: Common on IIS/Windows HTB boxes. The domain prefix is required for NTLM.
  Use credentials from earlier attacks (responder, kerberoasting).

## Scenario 37: Bearer token / JWT authentication
Method: test_injection
Args: {url: "http://<IP>/api/v1/items?id=1", headers: "Authorization: Bearer eyJhbGciOiJIUzI1NiJ9...", timeout: 300}
Expected: success=true, tests API endpoint with JWT auth
Notes: JWT tokens are passed via headers param. If the token expires during testing,
  use eval param with Python code to refresh it, or use csrf_url/csrf_token for
  CSRF-like token rotation.

## Scenario 38: CSRF token handling
Method: test_injection
Args: {url: "http://<IP>/form.php", data: "name=test&csrf_token=abc123", csrf_token: "csrf_token", csrf_url: "http://<IP>/form.php", timeout: 300}
Expected: success=true, auto-refreshes CSRF token for each request
Notes: csrf_token tells sqlmap which parameter contains the anti-CSRF token.
  csrf_url tells it where to GET a fresh token. Without this, requests after the
  first will fail with "invalid token" errors.

## Scenario 39: Eval-based dynamic parameter computation
Method: test_injection
Args: {url: "http://<IP>/page.php?id=1&hash=abc", eval: "import hashlib; hash=hashlib.md5(id.encode()).hexdigest()", timeout: 300}
Expected: success=true, recomputes hash for each id value
Notes: eval runs Python code before each request. Use when the app validates a hash
  or signature of the injectable parameter. The computed variable name must match
  the URL parameter name.

# The injection is sent via one URL, but the result appears on a different URL.

# ===============================================================================

## Scenario 40: Second-order injection
Method: test_injection
Args: {url: "http://<IP>/profile/edit.php", data: "bio=test", second_url: "http://<IP>/profile/view.php", timeout: 600}
Expected: success=true, detects injection via second_url response
Notes: The injection payload is submitted to edit.php but sqlmap reads the result
  from view.php. Common in "update profile" -> "view profile" flows where the bio
  field is stored and later interpolated into a SQL query on the view page.


# ===============================================================================
# TEST_INJECTION — DETECTION: SPECIFIC TECHNIQUES
# Restrict technique to test specific injection types. Useful for confirming
# specific vectors or when other techniques interfere.
# ===============================================================================

## Scenario 41: Union-based only detection
Method: test_injection
Args: {url: "http://<IP>/page.php?id=1", technique: "U", timeout: 300}
Expected: success=true, injection_type contains "UNION"
Notes: UNION-based is the fastest for data extraction (returns full rows in one
  request). If this works, always prefer it over blind techniques. Combine with
  union_cols if you know approximate column count from ORDER BY testing.

## Scenario 42: Union-based with column range hint
Method: test_injection
Args: {url: "http://<IP>/page.php?id=1", technique: "U", union_cols: "4-8", timeout: 300}
Expected: success=true, UNION injection with column count in range 4-8
Notes: Narrows the column search (default 1-20). If you ran ORDER BY manually and
  found 6 columns, use union_cols="5-7" to speed detection. Each column count
  requires a separate request.

## Scenario 43: Error-based only detection
Method: test_injection
Args: {url: "http://<IP>/page.php?id=1", technique: "E", timeout: 300}
Expected: success=true, injection_type contains "error-based"
Notes: Error-based extracts data from database error messages. Second fastest after
  UNION. Requires verbose error output (display_errors=On in PHP, detailed errors
  in ASP.NET). Works on MySQL (EXTRACTVALUE, UPDATEXML), MSSQL (CONVERT), PG (CAST).

## Scenario 44: Stacked queries only detection
Method: test_injection
Args: {url: "http://<IP>/page.php?id=1", technique: "S", timeout: 300}
Expected: success=true, injection_type contains "stacked"
Notes: Stacked queries (id=1;DROP TABLE--) allow arbitrary SQL execution including
  INSERT, UPDATE, DELETE, and DDL. Required for os_shell on MySQL (UDF creation).
  MSSQL supports stacked natively. MySQL requires multi-statement configuration.
  Most PHP+MySQL apps do NOT support stacked queries (mysqli_query is single-statement).

## Scenario 45: Inline query detection
Method: test_injection
Args: {url: "http://<IP>/page.php?id=1", technique: "Q", timeout: 300}
Expected: success=true, inline query injection detected
Notes: Inline queries inject a sub-query: id=(SELECT ...). Rare but works when
  the parameter is used directly as a value in the SQL query. Usually detected
  automatically, but restricting to Q is useful for confirmation.

## Scenario 46: Not-string for false response detection
Method: test_injection
Args: {url: "http://<IP>/page.php?id=1", not_string: "No results found", timeout: 300}
Expected: success=true, uses "No results found" as FALSE indicator
Notes: Complementary to --string. not_string appears in FALSE responses and is
  absent from TRUE responses. Use when the FALSE page has a unique message but
  the TRUE page content varies.

## Scenario 47: Through Burp Suite proxy
Method: test_injection
Args: {url: "http://<IP>/page.php?id=1", proxy: "http://127.0.0.1:8080", timeout: 600}
Expected: success=true, requests visible in Burp proxy log
Notes: Route through Burp for request inspection and replay. Useful for debugging
  when sqlmap reports "not injectable" but you suspect it should be. Double timeout
  because proxy adds latency.

## Scenario 48: Through SOCKS proxy (tunnel)
Method: test_injection
Args: {url: "http://172.16.0.10/page.php?id=1", proxy: "socks5://127.0.0.1:1080", timeout: 600}
Expected: success=true, reaches internal target through tunnel
Notes: For pivoting through compromised hosts. Set up SOCKS proxy via SSH tunnel
  tool first. Internal targets often have no WAF, so basic settings work.

## Scenario 49: Ignore non-200 status codes
Method: test_injection
Args: {url: "http://<IP>/page.php?id=1", ignore_code: "401,403", timeout: 300}
Expected: success=true, continues testing despite 401/403 responses
Notes: Critical when the target returns non-200 status for normal requests. Without
  ignore_code, sqlmap may refuse to test or produce false negatives. Common on
  API endpoints that return 401 for unauthenticated requests but are still injectable.

## Scenario 50: Null connection for faster boolean detection
Method: test_injection
Args: {url: "http://<IP>/page.php?id=1", null_connection: true, timeout: 300}
Expected: success=true, uses HTTP Range/HEAD for faster page comparison
Notes: null_connection avoids downloading full page body — uses Content-Length or
  HTTP Range header to compare responses. 2-5x faster for boolean-based blind.
  May not work if server does not support Range requests or returns same
  Content-Length for TRUE and FALSE.

## Scenario 51: Flush session to retest from scratch
Method: test_injection
Args: {url: "http://<IP>/page.php?id=1", flush_session: true, timeout: 300}
Expected: success=true, retests injection without cached results
Notes: sqlmap caches results in ~/.sqlmap/output/. If you changed the target
  (different box, different instance), flush_session forces a clean retest.
  Also use when sqlmap says "already tested" but you know the target has changed.


# ===============================================================================
# ENUMERATE_DBS — DATABASE ENUMERATION
# Method: enumerate_dbs — list all accessible databases
# Key output: databases[] list, count
# Engagement data: 1 call, 100% timeout (120s too low). Use 300-600s minimum.

## Scenario 108: Check secure_file_priv (MySQL)

## Scenario 126: os_shell fails (no stacked queries on MySQL)

Expected: success=false or timeout, os_shell requires stacked queries or UDF on MySQL
Notes: Most PHP+MySQL apps use mysqli_query which does not support stacked queries.

## Scenario 127: Expired session cookie
Method: test_injection

Notes: Expired cookies cause all requests to redirect to login page. sqlmap sees
  identical responses for TRUE and FALSE conditions. Symptom: "all tested
  parameters do not appear to be injectable" on a known-injectable endpoint.
  Solution: get fresh cookie and retry.

## Scenario 128: High latency causing time-based false positives
Method: test_injection
Args: {url: "http://<IP>/page.php?id=1", technique: "T", time_sec: 3, timeout: 600}
Expected: success=true but may report false positive vulnerability
Notes: Default time_sec=5 assumes <1s network latency. On high-latency VPN
  connections (100-200ms), time_sec=3 causes false positives because normal
  request variance overlaps with the injected delay. Use time_sec=10 minimum
  on VPN connections to avoid false positives.

## Scenario 129: Redirect loop (302 -> 302 -> ...)
Method: test_injection
Args: {url: "http://<IP>/page.php?id=1", timeout: 300}
Expected: success=true but may fail or produce unexpected results
Notes: If the target redirects after injection (e.g., INSERT then redirect to
  result page), sqlmap may follow the redirect and lose the injection response.
  Use second_url (Scenario 40) for these cases, or use --ignore-redirects.
