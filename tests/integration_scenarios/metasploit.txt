# Integration Scenarios: metasploit
# Required HTB Machines: Blue (10.10.10.40), Devel (10.10.10.5), Optimum (10.10.10.8)
# Recommended FIRST box: Blue (classic EternalBlue, exercises search_modules/check_vuln/
#   run_exploit/handler/list_sessions/session_command/post_module in a single chain)
# Prerequisites: Target reachable on VPN, msfrpcd running in container
# Run with: pytest tests/tools/test_metasploit.py -m integration --tool=metasploit \
#           --target=<IP> -v
#
# Data source: Trajectory analysis of 340 real metasploit calls across 9 engagements.
#   Method calls: session_command=178, list_sessions=79, run_exploit=43,
#     generate_payload=13, search_modules=11, handler=9, post_module=2, exec_command=2
#   Agent confusion: 3 calls to non-existent methods (start_handler, console_command,
#     run_command) -- all returned "method not found" errors gracefully
#   Error data: 0 tool-level failures (all 340 returned toolSuccess=true), but many
#     exploit attempts had exploit_success=false (especially local privesc modules)
#   Real exploits used: web_delivery (14 runs), cve_2024_30088 (17 runs),
#     cve_2024_35250 (6 runs), pgadmin_query_tool (3 runs), bad_successor (3 runs)
#   Session commands observed: getuid (34), shell (9), execute (many variants),
#     migrate (12), exit (6), ps (7), upload (6), hashdump, getsystem, load incognito
#
# Notes:
# - Metasploit container takes 2+ minutes to start (msfrpcd init + 30-retry connect)
# - Sessions persist across tool calls (service container via pymetasploit3 RPC)
# - All exploit/handler/check methods run via msfrpcd shared console (-j for bg jobs)
# - generate_payload uses msfvenom subprocess (stateless, most reliable method)
# - Payload shortcuts: windows_reverse_tcp, windows_reverse_https, linux_reverse_tcp,
#   linux_shell_tcp, php_reverse, java_reverse (resolved in _resolve_payload)
# - _classify_msf_error returns (error_class, retryable, suggestions) for structured
#   error handling: network (retryable), params (not), config (not)

## Scenario 12: MS17-010 vulnerability check (Blue)
# Box: Blue (10.10.10.40) - Windows 7 SP1, SMB vulnerable to EternalBlue
Method: check_vuln
Args: {module: "auxiliary/scanner/smb/smb_ms17_010", rhosts: "10.10.10.40", timeout: 120}
Expected: success=true, vulnerable=true, raw_output contains "VULNERABLE" or "[+]"
Notes: Classic MS17-010 check. The [+] line with "VULNERABLE" triggers positive detection.
  Parser logic: has_plus_vuln checks [+] lines, positive checks "is vulnerable"/"likely vulnerable",
  negated checks "not appear vulnerable"/"not vulnerable"/"does not appear".
