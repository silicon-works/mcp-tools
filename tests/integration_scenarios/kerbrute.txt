# CLOCK SKEW + FAKETIME OFFSET SCENARIOS
# =============================================================================
#
# Architecture: entrypoint.sh checks $FAKETIME env → sets LD_PRELOAD=/usr/lib/.../libfaketime.so.1
# The opensploit client's mcp-tool.ts passes clock_offset as a meta-parameter that becomes $FAKETIME.
# The server's base_server.py strips clock_offset from args before calling the handler.
#
# KEY INSIGHT from engagement data: Clock skew errors hit machine accounts (MS01$, EXCH01$) but
# NOT regular users (a.white, j.sparrow) in the SAME bruteforce call. This is because machine
# accounts with certain Kerberos pre-auth configurations are more sensitive to clock drift.
# userenum is LESS affected because it sends AS-REQ without pre-authentication data (no timestamp).
#
# Prompt guidance says "kerbrute does NOT need clock_offset — it treats clock skew as a valid-creds
# signal." This is INCORRECT for bruteforce/passwordspray against machine accounts, where the
# entire authentication attempt fails with KRB_AP_ERR_SKEW.

## Scenario 17: Detect clock skew error (machine accounts in bruteforce)
Method: bruteforce
Args: {dc: <DC_IP>, domain: <DOMAIN>, combos: "MS01$:ms01\nDC01$:dc01", safe: true, timeout: 30}
Expected: If DC clock offset >5 min: errors contain "KRB_AP_ERR_SKEW", error_class="config", retryable=true
Notes: Machine accounts trigger clock skew errors more readily than regular accounts. Pirate engagement:
       4 clock skew errors, ALL on machine accounts (MS01$, EXCH01$), ALL in bruteforce method.
       Regular users (a.white, j.sparrow) in same call got normal KDC_ERR_PREAUTH_FAILED.
STATUS [Certified 2026-04-08]: PARTIAL (no clock skew on Certified).
STATUS [Pirate 2026-04-20]: PASS — MS01$ got KRB_AP_ERR_SKEW, DC01$ got normal "Invalid password".
  error_class="config", retryable=true. Suggestions mention Go/FAKETIME limitation and userenum workaround.

## Scenario 18: FAKETIME correction for machine account clock skew
Method: bruteforce (with clock_offset passed at mcp_tool level)
Args: {dc: <DC_IP>, domain: <DOMAIN>, combos: "MS01$:ms01\nDC01$:dc01", clock_offset: "<detected_offset>", safe: true, timeout: 30}
Expected: success=true after FAKETIME correction, errors should NOT contain KRB_AP_ERR_SKEW
Notes: After detecting skew in Scenario 17, retry with clock_offset. clock_offset is a meta-parameter
       handled by opensploit client (mcp-tool.ts), NOT by the kerbrute server. The client sets
       FAKETIME env var on the container, which entrypoint.sh picks up via LD_PRELOAD + libfaketime.
       Flow: (1) bruteforce fails with clock skew, (2) detect offset with impacket.get_dc_time or
       nmap -sV -p 88 output, (3) retry with clock_offset: "+7h" (or whatever offset is needed).
STATUS [Certified 2026-04-08]: PARTIAL (FAKETIME has no effect on Go binary).
STATUS [Pirate 2026-04-20]: PASS — MS01$/EXCH01$ both get KRB_AP_ERR_SKEW. Suggestions correctly
  document FAKETIME/Go limitation and recommend userenum or --cap-add SYS_TIME + ntpdate.
