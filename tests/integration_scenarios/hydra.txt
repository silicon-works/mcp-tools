# Integration Scenarios: hydra
# Required HTB Machine: Any box with login services (see per-scenario recommendations)
# Recommended FIRST box: Nibbles (easy Linux, web form + SSH, exercises web_form_brute
#   and ssh_brute, fast runs, known password "nibbles")
# Prerequisites: Target reachable on VPN, at least one login service accessible
# Run with: pytest tests/tools/test_hydra.py -m integration --tool=hydra \
#           --target=<IP> -v
# WARNING: Brute-force can lock accounts. Use responsibly on HTB machines only.
#
# Data source: 32 hydra calls across 4 HTB engagements.
#   Method calls: ssh_brute=12, web_form_brute=9, bruteforce=6, ftp_brute=3, mysql_brute=2
#   Timeout rate: ssh_brute 47.4% (thread/wordlist too ambitious), others <10%
#   Common errors: SSH MaxStartups rate limiting (threads>4), web form wrong fail_string,
#     HTTPS downgrade to HTTP (now fixed), MySQL host blocked after max_connect_errors
#
# Server methods (5): bruteforce, ssh_brute, ftp_brute, web_form_brute, mysql_brute
# Password-only services (no username): redis, cisco, cisco-enable, oracle-listener, snmp, vnc
# Built-in wordlists: rockyou (14M), common-passwords (10K), default-passwords, usernames (~17)
# Special wordlist: ssh-usernames (30 common SSH users, generated at runtime)

# ===============================================================================
# SSH BRUTE-FORCE SCENARIOS (ssh_brute)
# Method: ssh_brute — convenience wrapper, defaults: threads=4, port=22, service=ssh
# Key constraint: SSH MaxStartups rate-limits to ~10 concurrent unauthenticated
#   connections. threads=4 is the safe maximum. threads>6 causes false negatives.
# Engagement data: 47.4% timeout rate — caused by large wordlists + insufficient
#   timeout. Use common-passwords (10K) not rockyou (14M) for SSH.
# ===============================================================================

## Scenario 1: SSH single credential validation
Method: ssh_brute
Args: {target: "<IP>", username: "admin", password: "admin", timeout: 30}
Expected: success=true, found=true/false, credentials list (0 or 1 entry)
Notes: Fastest possible test — single user:pass pair. Use to validate credentials
  found elsewhere (e.g., from config files, password reuse). 30s timeout is generous
  for a single attempt.

## Scenario 2: SSH try_common before wordlist (fast misconfig check)
Method: ssh_brute
Args: {target: "<IP>", username: "root", try_common: "nsr", timeout: 60}
Expected: success=true, tests null/same/reversed (3 attempts total)
Notes: Always run this first — tests root:null, root:root, root:toor in seconds.
  Catches misconfigured systems before committing to slow wordlist attacks.

## Scenario 3: SSH brute-force known username with password list
Method: ssh_brute
Args: {target: "<IP>", username: "root", passlist: "common-passwords", threads: 4, stop_on_first: true, timeout: 600}
Expected: success=true, stops on first valid credential
Notes: 10K passwords at 4 threads takes ~40 minutes. stop_on_first saves time.
  If this times out, increase timeout to 2400 or use a smaller targeted wordlist.

## Scenario 4: SSH brute-force with username list
Method: ssh_brute
Args: {target: "<IP>", userlist: "ssh-usernames", password: "password123", threads: 4, timeout: 120}
Expected: success=true, tests 30 SSH usernames against single password
Notes: Password spray — one password against many users. Fast (30 attempts).
  Use when you have a likely password but unknown username.

## Scenario 5: SSH brute-force with both lists (loop_users to avoid lockout)
Method: ssh_brute
Args: {target: "<IP>", userlist: "ssh-usernames", passlist: "common-passwords", loop_users: true, threads: 4, stop_on_first: true, timeout: 2400}
Expected: success=true, tries each password against all users before next password
Notes: Full matrix attack — 30 users x 10K passwords = 300K attempts. VERY slow.
  loop_users=true critical: if lockout threshold is 5, each user gets only 1 attempt
  per password cycle. 2400s (40 min) may still timeout — consider targeted list.

## Scenario 6: SSH non-standard port
Method: ssh_brute
Args: {target: "<IP>", username: "user", password: "test", port: 2222, timeout: 30}
Expected: success=true, connects to port 2222
Notes: HTB machines sometimes expose SSH on non-standard ports (nmap finds these).
  Always specify port when SSH is not on 22.

## Scenario 7: SSH with wait_time to avoid rate limiting
Method: ssh_brute
Args: {target: "<IP>", username: "admin", passlist: "common-passwords", threads: 4, wait_time: 2, stop_on_first: true, timeout: 1200}
Expected: success=true, slower but more reliable
Notes: wait_time=2 adds 2s delay between attempts per thread. Use when seeing
  "[ERROR] could not connect" or "Connection refused" in output. Doubles attack
  time but avoids MaxStartups drops. Increase timeout accordingly.

## Scenario 8: SSH verbose output for debugging
Method: ssh_brute
Args: {target: "<IP>", username: "admin", passlist: "common-passwords", verbose: true, threads: 4, stop_on_first: true, timeout: 600}
Expected: success=true, verbose_output field populated with attempt log
Notes: verbose=true includes last 1000 [ATTEMPT] lines. Use when credentials aren't
  found but expected — shows exactly what was tried. Warning: large output.

## Scenario 9: SSH password generation (PIN brute-force)
Method: ssh_brute
Args: {target: "<IP>", username: "root", password_gen: "4:4:1", threads: 4, stop_on_first: true, timeout: 1200}
Expected: success=true, generates all 4-digit PINs (10000 combinations)
Notes: password_gen overrides passlist. "4:4:1" = exactly 4 chars, digits only.
  Useful when custom apps use PIN-based SSH authentication.

## Scenario 10: SSH combo file (default credentials)
Method: ssh_brute
Args: {target: "<IP>", combo_file: "/usr/share/seclists/Passwords/Default-Credentials/ssh-betterdefaultpasslist.txt", stop_on_first: true, timeout: 300}
Expected: success=true, tests user:pass pairs from SecLists
Notes: combo_file (-C) provides pre-paired credentials. Each line is "user:pass".
  Overrides all username/password options. Best for testing default credentials.

## Scenario 11: SSH — service unreachable (error handling)
Method: ssh_brute
Args: {target: "<IP>", username: "root", password: "test", port: 9999, timeout: 30}
Expected: success=false, error_class="network", suggestions include "Verify the target is reachable"
Notes: Tests error handling when SSH is not on the specified port. Should fail
  quickly with a clear error message, not hang until timeout.

## Scenario 12: SSH — timeout with partial results
Method: ssh_brute
Args: {target: "<IP>", username: "root", passlist: "rockyou", threads: 4, timeout: 30}
Expected: success=false, partial=true, error_class="timeout", any found creds in data
Notes: rockyou (14M) with 30s timeout will always timeout. Tests partial result
  recovery — credentials found before timeout should still be returned. Retryable=true.

## Scenario 19: FTP multiple users with password spray
Method: ftp_brute
Args: {target: "<IP>", userlist: "usernames", password: "Password1!", loop_users: true, threads: 8, timeout: 120}
Expected: success=true, sprays one password across all users

## Scenario 20: FTP password generation (short passwords)
Method: ftp_brute
Args: {target: "<IP>", username: "admin", password_gen: "1:4:a1", threads: 8, stop_on_first: true, timeout: 600}
Expected: success=true, generates 1-4 char lowercase+digit passwords
Notes: password_gen "1:4:a1" = min 1, max 4, lowercase + digits. Generates ~1.7M
  combinations — suitable for FTP (fast connections) but not SSH (too slow).

# ===============================================================================
# WEB FORM BRUTE-FORCE SCENARIOS (web_form_brute)
# Method: web_form_brute — builds hydra http-post-form attack string automatically
# Requires: path, fail_string (minimum). Auto-constructs:
#   "/path:user_field=^USER^&pass_field=^PASS^[&extra]:F=fail_string"
# Colon escaping: literal colons in path/values escaped as \: internally
# Default fields: user_field="username", pass_field="password"
# Default threads: 16 (web servers handle concurrency well)
# DOES NOT handle: CSRF tokens (dynamic), JavaScript-based logins, CAPTCHAs
# ===============================================================================

## Scenario 21: Basic web form brute-force (POST)
Method: web_form_brute
Args: {target: "<IP>", path: "/login.php", fail_string: "Invalid", username: "admin", passlist: "common-passwords", threads: 16, stop_on_first: true, timeout: 300}
Expected: success=true, found=true if password in wordlist
Notes: Standard HTTP POST form attack. fail_string is the key differentiator —
  must appear ONLY on failed login responses. Test by submitting bad creds manually.

## Scenario 22: Web form with custom field names
Method: web_form_brute
Args: {target: "<IP>", path: "/auth/login", user_field: "email", pass_field: "passwd", fail_string: "Login failed", username: "admin@target.htb", passlist: "common-passwords", stop_on_first: true, timeout: 300}
Expected: success=true, custom field names used in POST body
Notes: Not all forms use "username"/"password". Inspect HTML source for <input name="...">
  attributes. Email-based logins are increasingly common (user_field="email").

## Scenario 23: HTTPS web form brute-force
Method: web_form_brute
Args: {target: "<IP>", path: "/login", fail_string: "incorrect", username: "admin", passlist: "common-passwords", https: true, stop_on_first: true, timeout: 300}
Expected: success=true, uses https-post-form service, port defaults to 443
Notes: https=true switches service to https-post-form and port to 443. Previously
  there was a silent downgrade bug where HTTPS targets were attacked over HTTP —
  this has been fixed. Verify by checking service field in response summary.

## Scenario 24: HTTPS on non-standard port
Method: web_form_brute
Args: {target: "<IP>", path: "/login", fail_string: "Invalid", username: "admin", password: "admin", https: true, port: 8443, timeout: 30}
Expected: success=true, connects to port 8443 with HTTPS
Notes: Common non-standard HTTPS ports: 8443, 4443, 9443. Must set both
  https=true AND port=8443 (https only changes service name and default port).

## Scenario 25: Web form with extra POST parameters
Method: web_form_brute
Args: {target: "<IP>", path: "/login.php", fail_string: "Invalid credentials", username: "admin", passlist: "common-passwords", extra_params: "submit=Login&remember=1", threads: 16, stop_on_first: true, timeout: 300}
Expected: success=true, extra POST params included in every request
Notes: Some forms require hidden fields (submit button value, remember-me checkbox).
  extra_params are appended to the POST body. For static CSRF tokens, include here —
  but dynamic CSRF tokens will fail (hydra can't extract per-request tokens).

## Scenario 26: Password spraying across users on web form
Method: web_form_brute
Args: {target: "<IP>", path: "/login.php", fail_string: "Invalid", userlist: "usernames", password: "Password1!", loop_users: true, threads: 8, timeout: 300}
Expected: success=true, sprays one password across all users
Notes: Password spraying — one password against many users before moving to next.
  loop_users=true prevents lockout. Reduce threads to 8 to avoid suspicion.

## Scenario 27: Web form — path with colon (URL edge case)
Method: web_form_brute
Args: {target: "<IP>", path: "/app:8080/login", fail_string: "denied", username: "admin", password: "admin", timeout: 30}
Expected: success=true, colon in path escaped correctly as \: in hydra form string
Notes: Hydra uses colons as delimiters in form strings. The server's _escape_colon()
  handles this: /app:8080/login becomes /app\:8080/login in the hydra command.
  Tests correct colon escaping in the path component.

## Scenario 28: Web form — fail_string with colon
Method: web_form_brute
Args: {target: "<IP>", path: "/login", fail_string: "Error: invalid credentials", username: "admin", password: "admin", timeout: 30}
Expected: success=true, colon in fail_string escaped correctly
Notes: fail_string "Error: invalid credentials" contains a colon. The server
  escapes it to "Error\: invalid credentials" so hydra's delimiter parsing works.

## Scenario 29: Web form — success_string approach (workaround)
Method: bruteforce
Args: {target: "<IP>", service: "http-post-form", http_form: "/login.php:username=^USER^&password=^PASS^:S=Dashboard", username: "admin", passlist: "common-passwords", threads: 16, stop_on_first: true, timeout: 300}
Expected: success=true, uses S= (success string) instead of F= (fail string)
Notes: web_form_brute only supports F= (fail_string). When the failure response is
  hard to match but the success response has a unique string (e.g., "Dashboard",
  "Welcome"), use bruteforce directly with http_form containing S= prefix.
  S= means "success if this string appears" (opposite of F=).

## Scenario 30: Web form — GET form (query parameter login)
Method: bruteforce
Args: {target: "<IP>", service: "http-get-form", http_form: "/login.php:user=^USER^&pass=^PASS^:F=Invalid", username: "admin", passlist: "common-passwords", threads: 16, stop_on_first: true, timeout: 300}
Expected: success=true, uses GET parameters instead of POST body
Notes: Some legacy apps use GET-based login forms (parameters in URL). Use
  http-get-form service via bruteforce directly. web_form_brute always uses POST.

## Scenario 31: HTTP basic auth brute-force
Method: bruteforce
Args: {target: "<IP>", service: "http-get", http_path: "/admin", username: "admin", passlist: "common-passwords", threads: 16, stop_on_first: true, timeout: 300}
Expected: success=true, tests HTTP Basic Authentication
Notes: HTTP Basic Auth (401 popup) uses http-get service, NOT http-post-form.
  Common on Tomcat (/manager/html), Nagios (/nagios), router admin panels.
  http_path specifies the protected resource. No fail_string needed.

## Scenario 32: HTTPS basic auth brute-force
Method: bruteforce
Args: {target: "<IP>", service: "https-get", http_path: "/admin", username: "admin", passlist: "common-passwords", threads: 16, stop_on_first: true, timeout: 300}
Expected: success=true, tests HTTPS Basic Authentication
Notes: Same as Scenario 31 but over HTTPS. Use https-get service.

## Scenario 33: Web form — wrong fail_string (false positive trap)
Method: web_form_brute
Args: {target: "<IP>", path: "/login.php", fail_string: "Welcome", username: "admin", password: "wrongpassword", timeout: 30}
Expected: success=true, found=false (correctly rejects — "Welcome" appears on success page)
Notes: CRITICAL EDGE CASE: if fail_string matches the SUCCESS page, every attempt
  looks like a failure — zero results. If fail_string matches BOTH pages, hydra
  can't distinguish success from failure. Always verify fail_string is unique to
  the failure response by manually testing with known-bad credentials.

## Scenario 34: Web form — empty fail_string behavior
Method: web_form_brute
Args: {target: "<IP>", path: "/login.php", fail_string: "", username: "admin", password: "test", timeout: 30}
Expected: success=true or error depending on hydra behavior with empty F=
Notes: Edge case: empty fail_string. Hydra may match everything or nothing.
  The server does not validate fail_string is non-empty — hydra's behavior
  determines the outcome. Document actual behavior when tested.

## Scenario 35: Web form — WordPress brute-force
Method: web_form_brute
Args: {target: "<IP>", path: "/wp-login.php", user_field: "log", pass_field: "pwd", fail_string: "Invalid username", username: "admin", passlist: "common-passwords", stop_on_first: true, timeout: 300}
Expected: success=true, found if password in list
Notes: WordPress login: path=/wp-login.php, user_field=log, pass_field=pwd.
  fail_string "Invalid username" works when username exists but password wrong.
  If unsure about username, try fail_string="lost your password" (appears on
  failure page). For production WordPress pentesting, wpscan is preferred.

## Scenario 36: MySQL root empty password
Method: mysql_brute
Args: {target: "<IP>", username: "root", try_common: "n", timeout: 30}
Expected: success=true, found=true if root has empty password
Notes: Most important MySQL check — root with no password. try_common="n" tests
  only null password (1 attempt, instant). Common on dev/test systems.

## Scenario 37: MySQL root with common passwords
Method: mysql_brute
Args: {target: "<IP>", username: "root", passlist: "common-passwords", threads: 4, stop_on_first: true, timeout: 600}
Expected: success=true, root password found if in 10K wordlist
Notes: After empty password fails, try common-passwords. 10K passwords at 4
  threads takes ~20 minutes for MySQL. stop_on_first recommended.

## Scenario 38: MySQL multiple users
Method: mysql_brute
Args: {target: "<IP>", userlist: "usernames", password: "password", threads: 4, timeout: 120}
Expected: success=true, tests ~17 common usernames with single password
Notes: Password spray against MySQL. Tests admin, root, user, etc. with "password".
  When userlist is provided, the default username="root" is overridden.

## Scenario 39: MySQL default credential combo file
Method: mysql_brute
Args: {target: "<IP>", combo_file: "/usr/share/seclists/Passwords/Default-Credentials/mysql-betterdefaultpasslist.txt", stop_on_first: true, timeout: 300}
Expected: success=true, tests MySQL-specific default credentials
Notes: SecLists MySQL default credentials — pre-paired user:pass combinations.
  Fastest way to find default MySQL credentials.

## Scenario 40: MySQL non-standard port
Method: mysql_brute
Args: {target: "<IP>", username: "root", password: "root", port: 3307, timeout: 30}
Expected: success=true, connects to port 3307
Notes: MariaDB and some MySQL configurations use 3307. Also common when
  multiple MySQL instances run on the same host (3306, 3307, 3308).

## Scenario 41: MySQL — host blocked after many failures (error handling)
Method: mysql_brute
Args: {target: "<IP>", username: "root", passlist: "common-passwords", threads: 4, timeout: 600}
Expected: After ~100 failed attempts, may see "[ERROR] Host is blocked" or connection errors
Notes: MySQL's max_connect_errors blocks hosts after too many failures. If you
  see this error, the host must be unblocked (FLUSH HOSTS) or you must wait.
  Use smaller wordlists or test from a different source IP. Error class: "network".

# --- RDP (Remote Desktop Protocol) ---

## Scenario 42: RDP brute-force (Windows target)
Method: bruteforce
Args: {target: "<IP>", service: "rdp", username: "Administrator", passlist: "common-passwords", threads: 4, stop_on_first: true, timeout: 600}
Expected: success=true, found if password in list
Notes: RDP brute-force against Windows targets. Very slow — RDP has high latency
  per attempt. Default 4 threads is correct. 10K passwords takes 30+ minutes.
  Always test "Administrator" first, then domain users if found.

## Scenario 43: RDP with domain user
Method: bruteforce
Args: {target: "<IP>", service: "rdp", username: "DOMAIN\\user", passlist: "common-passwords", threads: 4, stop_on_first: true, timeout: 600}
Expected: success=true, domain credentials tested
Notes: For domain-joined Windows: use DOMAIN\\user format. Hydra passes this
  as the username to RDP. If domain is unknown, try the machine's hostname.

## Scenario 44: RDP password spray (multiple users)
Method: bruteforce
Args: {target: "<IP>", service: "rdp", userlist: "usernames", password: "Welcome1!", loop_users: true, threads: 4, timeout: 600}
Expected: success=true, tests multiple users with common AD password
Notes: Active Directory password spray via RDP. loop_users=true critical to avoid
  lockout (default AD policy: 5 failed attempts). "Welcome1!" is a common
  initial/reset password in corporate environments.

Expected: success=true, found=true/false
Notes: VNC is a PASSWORD-ONLY service — no username. Hydra only uses -p/-P flags.

## Scenario 50: VNC non-standard port

# --- Redis ---

## Scenario 51: Redis password brute-force (password-only service)
Method: bruteforce
Args: {target: "<IP>", service: "redis", password: "foobared", timeout: 30}
Expected: success=true, found=true if Redis uses default password "foobared"
Notes: Redis is PASSWORD-ONLY — no username. "foobared" is Redis's historical

## Scenario 52: Redis with password list
Method: bruteforce
Args: {target: "<IP>", service: "redis", passlist: "common-passwords", threads: 8, stop_on_first: true, timeout: 300}
Expected: success=true, found if Redis password in list
Notes: Redis handles 8 threads well (in-memory, fast auth). Redis with weak
  passwords is a common HTB vector for RCE (write SSH keys, module load, etc.).

## Scenario 53: Redis null password check
Method: bruteforce
Args: {target: "<IP>", service: "redis", try_common: "n", timeout: 30}
Expected: success=true, found=true if no password required
Notes: Test for unprotected Redis (no AUTH). If found=true with null password,
  Redis is open — proceed to data extraction or RCE.

## Scenario 71: Thread count impact on SSH (too many threads)
Method: ssh_brute
Args: {target: "<IP>", username: "root", passlist: "common-passwords", threads: 16, timeout: 120}
Expected: success=true but may see warnings about "could not connect" or false negatives
Notes: ANTI-PATTERN SCENARIO. threads=16 on SSH exceeds MaxStartups, causing
  dropped connections. Hydra may report "[ERROR] could not connect to ssh" for
  many attempts. Compare results with threads=4 to see the difference.

## Scenario 72: wait_time for IDS evasion
Method: bruteforce
Args: {target: "<IP>", service: "ssh", username: "root", passlist: "common-passwords", threads: 4, wait_time: 3, stop_on_first: true, timeout: 3600}
Expected: success=true, much slower but stealthier
Notes: wait_time=3 adds 3 seconds between attempts per thread. At 4 threads with
  3s wait, throughput drops to ~1.3 attempts/second. 10K passwords takes ~2 hours.
  Use for targets with IDS/IPS that detect rapid login attempts. Increase timeout.

## Scenario 73: Credential reuse across services
Method: bruteforce
Args: {target: "<IP>", service: "smb", username: "admin", password: "P@ssw0rd123", timeout: 30}
Expected: success=true, found=true/false
Notes: After finding valid credentials on one service (e.g., SSH admin:P@ssw0rd123),
  test the same credentials on other services. Password reuse is extremely common.
  Test: SSH, FTP, SMB, RDP, MySQL, web forms — all with the same credentials.

## Scenario 74: Large wordlist timeout recovery
Method: bruteforce
Args: {target: "<IP>", service: "ftp", username: "admin", passlist: "rockyou", threads: 8, stop_on_first: true, timeout: 60}
Expected: success=false, partial=true, retryable=true, any found creds preserved
Notes: rockyou (14M entries) with 60s timeout. Tests partial result recovery.
  The response should have partial=true and include any credentials found before
  timeout. Agent should use this as a signal to switch to a smaller wordlist.

## Scenario 75: Service not running (connection refused)

Expected: success=false, error_class="network", error contains "could not connect"
Notes: When MySQL isn't running or port is closed. Should fail fast with clear
  network error. Suggestions should include "Verify the target is reachable".
