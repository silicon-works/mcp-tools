# Integration Scenarios: enum4linux-ng
# Recommended HTB Machine: Garfield (retired) — see recommendation at end of file
# Alternatives: Active, Forest, Overwatch, Cascade, Sauna, Resolute, Monteverde
# Prerequisites: VPN connected, target IP reachable on port 445 or 139
# Run with: pytest tests/tools/test_enum4linux_ng.py -m integration --tool=enum4linux-ng \
#           --target=<IP> [-v] [--username=<USER> --password=<PASS>]
#
# Placeholders:
#   <IP>             = Target IP (e.g., 10.129.232.137)
#   <USER>           = Domain user (e.g., j.arbuckle)
#   <PASS>           = Password for <USER>
#   <DOMAIN>         = NetBIOS domain name (e.g., GARFIELD)
#   <FILTERED_IP>    = IP where SMB is firewalled (SYN dropped, no RST)
#
# Method Coverage (5 methods, all covered):
#   enumerate   : Scenarios 1, 7, 16, 20, 21, 22, 26, 28, 30
#   enum_users  : Scenarios 3, 6, 9, 17, 23, 27
#   enum_shares : Scenarios 2, 8, 14, 15, 18, 24
#   enum_groups : Scenarios 4, 19
#   enum_policy : Scenarios 5, 10, 25
#
# Known Bugs Surfaced by Engagement Data (verify fixes):
#   BUG-1: enum_users -R flag consumes rid_range string as BULK_SIZE (Pirate engagement,
#          March 2026). Error: "argument -R: invalid int value: '500-550,1000-1200'".
#          Root cause: argparse nargs='?' on -R grabs the next positional-looking token.
#          Fix: place -r <range> BEFORE -R in the command, or separate with target.
#          Regression test exists: TestRidRangeBugRegression.test_rid_range_not_passed_to_R_flag
#   BUG-2: Parsed JSON returns empty shares/users/groups despite successful raw output
#          (Overwatch, Garfield, Pirate engagements). enum4linux-ng writes JSON to
#          <base_path>.json but _parse_json_output may read wrong path or file is
#          incomplete when process exits mid-enumeration. Scenario 30 specifically tests this.

# NULL SESSION SCENARIOS (anonymous, no credentials)
# ═══════════════════════════════════════════════════════════════════════════════

## Scenario 1: Full null session enumeration
Method: enumerate
Args: {target: <IP>, shares: true, users: true, groups: true, timeout: 120}
Expected: success=true on permissive targets (Active, Forest); classified error on restricted ones
Notes: First tool to run after nmap confirms port 445 open. Many Windows DCs allow null sessions.
HTB boxes: Active (10.10.10.100), Forest (10.10.10.161) -- both allow null session enumeration.

## Scenario 2: Null session share enumeration
Method: enum_shares
Args: {target: <IP>, timeout: 120}
Expected: success=true with shares array containing IPC$ at minimum
Notes: Even restricted targets often expose share names. Look for non-default shares
  (anything besides ADMIN$, C$, IPC$, print$, SYSVOL, NETLOGON).
HTB boxes: Active -- null session exposes "Replication" share with readable GPP XML.
Validate: shares[].access field present with mapping and listing values.

## Scenario 3: Null session user enumeration (RID cycling)
Method: enum_users
Args: {target: <IP>, rid_range: "500-550,1000-1200", timeout: 120}
Expected: success=true with at least Administrator (RID 500) and Guest (RID 501)
Notes: RID cycling works through null sessions where RPC user listing may be blocked.
  Well-known RIDs: 500=Administrator, 501=Guest, 502=krbtgt.
HTB boxes: Active -- discovers SVC_TGS, Administrator, Guest, krbtgt, svc_admin.
BUG-1 regression: Verify the command builds correctly and does not error with
  "invalid int value". Check raw_output for "usage:" error string.

## Scenario 4: Null session group enumeration
Method: enum_groups
Args: {target: <IP>, timeout: 120}
Expected: success=true with Domain Admins, Domain Users at minimum
Notes: Group enumeration reveals privilege structure. Key targets:
  Domain Admins, Remote Desktop Users, Backup Operators.
HTB boxes: Forest (10.10.10.161) -- exposes full AD group hierarchy.

## Scenario 5: Null session password policy
Method: enum_policy
Args: {target: <IP>, timeout: 120}
Expected: success=true with password_policy containing lockout threshold, min length
Notes: MUST check before brute-force. If lockout threshold=0, aggressive spray is safe.
  If threshold is 3-5, use careful password spraying with wait between attempts.
HTB boxes: Active -- lockout threshold=0 (no lockout), min length=7.

## Scenario 6: Extended RID range for large domains
Method: enum_users
Args: {target: <IP>, rid_range: "500-550,1000-5000", timeout: 300}
Expected: success=true with more users than default range
Notes: Default range (500-550,1000-1200) misses users with RID > 1200.
  Large AD domains may have hundreds of users with RIDs up to 10000+.
  Increase timeout for large ranges.
HTB boxes: Forest -- has service accounts in higher RID ranges.
BUG-1 regression: Extended ranges are the most common trigger for the -R bug.

Engagement data: Overwatch -- guest session found software$ share (Mapping OK, Listing OK).
  This is the high-value non-default share to investigate.

## Scenario 11: Wrong credentials
Method: enumerate
Args: {target: <IP>, username: "nonexistent", password: "wrongpass", timeout: 30}
Expected: error_class=auth, retryable=false, suggestions mention "null session"
Notes: STATUS_LOGON_FAILURE should be classified as auth error.

## Scenario 12: Unreachable target (connection refused)
Method: enumerate
Args: {target: "192.0.2.1", timeout: 15}
Expected: error_class=network, retryable=true, suggestions mention "nmap"
Notes: RFC 5737 TEST-NET-1 address, guaranteed unreachable.

## Scenario 13: Timeout on filtered port
Method: enumerate
Args: {target: <FILTERED_IP>, timeout: 15}
Expected: error_class=network, retryable=true, suggestions mention "timeout" or "firewall"
Notes: Use an IP where SMB port is firewalled (no RST, no SYN-ACK -- just drops).
  Timeout should trigger within the specified timeout period.

## Scenario 14: Guest session (empty username)
Method: enum_shares
Args: {target: <IP>, username: "guest", password: "", timeout: 120}
Expected: Varies by target -- success or auth error. Should not crash.
Notes: Some targets allow guest sessions with more access than null sessions.
  Useful when null session is blocked but guest is allowed.
Engagement data: Overwatch -- guest session allowed, discovered 6 shares. Hint in
  raw output: "Rerunning enumeration with user '<random>' might give more results".

## Scenario 15: Concurrent enumeration methods
Method: enumerate + enum_policy (sequential)
Args: {target: <IP>, timeout: 120} for both
Expected: Both succeed independently, no resource contention
Notes: In real pentesting, the agent runs multiple enumeration methods.
  Verify the container handles sequential calls correctly.

## Scenario 16: Null session on restricted target (access denied)
Method: enumerate
Args: {target: <IP>, shares: true, users: true, groups: true, timeout: 120}
Expected: success=true with partial data OR success=false with error_class=auth
Notes: Pirate engagement showed null session allowed (RPC session established) but
  STATUS_ACCESS_DENIED for querydispinfo, enumdomusers, enumalsgroups, enumdomgroups.
  Server still returned success=true with empty data -- should at least convey the
  partial failure. Users/groups/shares all empty. Domain SID still obtained.
HTB boxes: Resolute (10.10.10.169), Pirate (retired).
Engagement data: Pirate -- null session established but all enumeration denied.
  Found 0 shares "for user '' with password '', try a different user".

## Scenario 17: RID cycling on restricted target
Method: enum_users
Args: {target: <IP>, rid_range: "500-550,1000-1200", timeout: 120}
Expected: success=true with users discovered via RID cycling despite RPC user listing being blocked
Notes: This is the primary value of RID cycling -- it works even when STATUS_ACCESS_DENIED
  blocks direct user listing. The tool should fall through from querydispinfo/enumdomusers
  failure to RID cycling.
HTB boxes: Resolute -- null session blocks user listing but RID cycling works.
Engagement data: Pirate -- enum_users failed entirely due to BUG-1. After fix,
  re-test to see if RID cycling can retrieve users despite RPC access denial.

## Scenario 18: Authenticated enum_shares after null failure
Method: enum_shares
Args: {target: <IP>, username: <USER>, password: <PASS>, timeout: 120}
Expected: success=true with more shares than null session
Notes: When null session returns 0 shares, retry with discovered credentials.
  This is the standard escalation pattern.
Engagement data: Overwatch -- null session returned 0 shares, guest session found 6
  (ADMIN$, C$, IPC$, NETLOGON, SYSVOL, software$). Authenticated session may find more.

## Scenario 19: Authenticated group enumeration with members (-Gm equivalent)
Method: enum_groups
Args: {target: <IP>, username: <USER>, password: <PASS>, timeout: 120}
Expected: success=true with groups[] containing members arrays
Notes: Group membership is critical for privilege escalation path analysis.
  Key groups: Domain Admins, Backup Operators, Remote Desktop Users.
Engagement data: Garfield -- found Domain Admins, IT Support, Tier 1, RODC Administrators,
  DnsAdmins, DnsUpdateProxy. Members reveal who has admin access.

## Scenario 20: Enumerate with only shares disabled
Method: enumerate
Args: {target: <IP>, shares: false, users: true, groups: true, timeout: 120}
Expected: success=true, summary.shares is empty, users and groups populated
Notes: Verify selective module enabling works. When shares=false but users=true
  and groups=true, only -U and -G flags should be passed (not -S).

## Scenario 21: Enumerate with nothing enabled (defaults to -A)
Method: enumerate
Args: {target: <IP>, shares: false, users: false, groups: false, timeout: 120}
Expected: success=true with comprehensive data (all modules run via -A)
Notes: Code path: when all booleans are false, server defaults to -A (all simple
  enumeration). Verify this produces complete results including OS info, policy,
  NetBIOS names, LDAP info -- not just shares/users/groups.

## Scenario 22: SMB signing required target
Method: enumerate
Args: {target: <IP>, timeout: 120}
Expected: success=true, raw output shows "SMB signing required: true"
Notes: All engagement targets (Garfield, Overwatch, Pirate, Fries) had SMB signing
  required. Verify the tool handles this correctly (it does -- signing does not
  block enumeration, only relay attacks).
Engagement data: All four DC targets showed "SMB signing required: true" in raw output.

## Scenario 23: RID cycling with single range (no comma)
Method: enum_users
Args: {target: <IP>, rid_range: "500-1500", timeout: 120}
Expected: success=true, users discovered
Notes: Verify the tool handles a single continuous range without comma separation.
  This is a valid input that should work.

## Scenario 24: Null session on non-domain target (Samba/Linux)
Method: enum_shares
Args: {target: <SAMBA_IP>, timeout: 120}
Expected: success=true or classified error
Notes: enum4linux-ng works on Samba targets too, not just Windows DCs. Behavior
  differs: no domain SID, no RID cycling, different share names. HTB Linux boxes
  with SMB: Lame (legacy), Kenobi, FriendZone.
HTB boxes: Lame (10.10.10.3) -- Samba 3.0.20, famous CVE-2007-2447.

## Scenario 25: Password policy on target without policy
Method: enum_policy
Args: {target: <IP>, timeout: 120}
Expected: success=true with empty or minimal policy
Notes: Non-DC targets or Samba may not expose password policy via RPC.
  Verify the tool returns cleanly with empty policy rather than erroring.
Engagement data: Pirate and Garfield both returned empty policy{} despite
  successful raw output in Garfield case -- possible BUG-2 JSON parsing issue.

## Scenario 26: Null-then-auth escalation chain
Method: enumerate (twice)
Args:
  Step 1: {target: <IP>, shares: true, users: true, groups: true, timeout: 120}
  Step 2: {target: <IP>, username: <USER>, password: <PASS>, shares: true, users: true, groups: true, timeout: 120}
Expected: Step 2 returns >= Step 1 data (strict superset or equal)
Notes: Standard escalation: run null session first, discover creds elsewhere (GPP, LDAP,
  web app), then re-enumerate with creds. Compare user counts, share counts, group detail.
Engagement chain: Active -- null session finds Replication share → GPP creds →
  authenticated enum → SVC_TGS kerberoast → Admin.

## Scenario 27: enum_users → hydra password spray chain
Method: enum_users
Args: {target: <IP>, rid_range: "500-550,1000-2000", timeout: 300}
Expected: success=true with usernames extracted for hydra
Notes: The user list from enum_users feeds directly into hydra password spraying.
  Verify output format: users[].username is a simple string, usable as-is in hydra -L.
  Also verify enum_policy was checked first (lockout threshold).
Engagement chain: Forest -- enum_users → discover svc-alfresco → AS-REP roast.

## Scenario 28: Full enumeration → attack surface assessment
Method: enumerate
Args: {target: <IP>, username: <USER>, password: <PASS>, shares: true, users: true, groups: true, timeout: 300}
Expected: Complete picture: shares with access, users with RIDs, groups with membership
Notes: Cross-reference results to build attack surface:
  - Users in Domain Admins → high-value targets
  - Readable shares → loot for credentials/configs
  - Password policy → brute-force feasibility
  - OS info → known CVEs
Engagement data: Garfield -- authenticated enumerate found krbtgt_8245 (RODC KDC account,
  unusual), l.wilson_adm (admin account pattern "_adm"), IT Support group (lateral movement),
  Tier 1 group (possible delegation). These findings drive next steps.

## Scenario 29: Verify structured data matches raw output
Method: enum_shares
Args: {target: <IP>, username: <USER>, password: <PASS>, timeout: 120}
Expected: len(data.shares) > 0 AND data.shares matches shares in raw_output
Notes: BUG-2 validation. The structured shares array should contain all shares
  visible in the raw text output. Parse raw_output for "Found N share(s)" and
  compare with data.shares count.
Engagement data: Overwatch -- raw output showed 6 shares, structured data had 0.
  This scenario explicitly catches the discrepancy.

## Scenario 30: Verify JSON file written and parsed correctly
Method: enumerate
Args: {target: <IP>, shares: true, users: true, groups: true, timeout: 120}
Expected: data.full_results is non-empty when raw output shows successful enumeration
Notes: BUG-2 root cause investigation. Check that:
  1. raw_output contains "[+]" lines (successful enumeration happened)
  2. data.full_results is not empty (JSON file was written and parsed)
  3. data.summary.users/shares/groups counts match full_results
  If raw output shows data but full_results is empty, the JSON file was not created
  or was not found at the expected path.
Engagement data: Garfield, Pirate, Fries all showed successful raw output but empty
  parsed results. This scenario validates the JSON pipeline end-to-end.
