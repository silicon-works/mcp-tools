# Engagement data: 18 calls (56% of all ffuf usage).

## Scenario 1: Basic directory fuzzing with common wordlist
Method: dir_fuzz
Args: {url: "http://<IP>/FUZZ", wordlist: "common"}
Expected: success=true, results contains entries with status 200/301/302/403
Notes: Standard first-step directory scan. The common wordlist has 4,614 entries
  and completes in under 60s on most targets. 6 of 18 real dir_fuzz calls used
  common without extensions. This is the fast-pass before adding extensions.

## Scenario 2: Directory fuzzing with auto FUZZ keyword insertion
Method: dir_fuzz
Args: {url: "http://<IP>/", wordlist: "common"}
Expected: success=true, server auto-appends FUZZ -> "http://<IP>/FUZZ"
Notes: Tests the FUZZ keyword auto-insertion. The mcp-server.py code strips
  trailing slash and appends /FUZZ if not present. Agent sometimes forgets FUZZ.

## Scenario 3: PHP target extensions (common HTB pattern)
Method: dir_fuzz
Args: {url: "http://<IP>/FUZZ", wordlist: "common", extensions: "php,html,txt,bak"}
Expected: success=true, results may contain index.php, config.php.bak, etc.
Notes: Most common extension set from engagements. Used on CCTV (ZoneMinder),
  Variatype portal, and multiple tunnel targets. 4 extensions x 4,614 words =
  ~23K requests. Completes in ~4 minutes.

## Scenario 4: IIS/ASP target extensions (Pirate HTB pattern)
Method: dir_fuzz
Args: {url: "http://<IP>/FUZZ", wordlist: "common", extensions: "asp,aspx,html,txt,config"}
Expected: success=true, finds .aspx pages, web.config, etc.
Notes: Exact pattern from Pirate HTB (IIS 10.0). 5 extensions. The "config"
  extension catches web.config, app.config, machine.config. Real engagement found
  aspx pages via this scan. Also used: "asp,aspx,html,txt,bak,old,config" (7 exts).

## Scenario 5: Broad extension scan (10 extensions)
Method: dir_fuzz
Args: {url: "http://<IP>/FUZZ", wordlist: "big", extensions: "php,html,txt,bak,conf,xml,json,js,py,sh"}
Expected: success=true, comprehensive but slower scan
Notes: Real pattern from CCTV HTB engagement. 10 extensions x 20,469 words =
  ~225K requests. Takes 30-40 minutes. The big wordlist finds paths that common
  misses. Used when initial common scan is sparse.

## Scenario 6: Extension count explosion (too many extensions - timeout risk)
Method: dir_fuzz
Args: {url: "http://<IP>/FUZZ", wordlist: "common", extensions: "php,phps,bak,txt,html,conf,cfg,ini,inc,old,orig,save,log,sql,xml,json"}
Expected: success=true OR timeout (16 extensions x 4,614 = 73K requests)
Notes: Real call from engagement timed out. This tests the _estimate_timeout()
  calculation. With 16 extensions, even the common wordlist produces 73K requests
  taking ~12 minutes at 100 req/s. Agent should use 4-6 targeted extensions.
  Also validates graceful timeout handling (error_class="timeout", retryable=true).

## Scenario 7: Dot-prefixed extensions (LLM parameter mistake)
Method: dir_fuzz
Args: {url: "http://<IP>/FUZZ", wordlist: "common", extensions: ".php,.html,.txt"}
Expected: success=true, ffuf handles dot-prefixed extensions correctly
Notes: Agent used dot-prefixed extensions in 3 real calls. ffuf adds its own dot,
  so ".php" becomes "..php" in the actual request. ffuf -e actually strips leading
  dots, so this works but is a documentation/prompt clarity issue. Both formats
  should produce identical results. Test both to confirm.

## Scenario 8: Big wordlist directory fuzzing
Method: dir_fuzz
Args: {url: "http://<IP>/FUZZ", wordlist: "big"}
Expected: success=true, more paths than common wordlist
Notes: 20,469 entries. 3 real calls used "big" wordlist. Takes 3-4 minutes without
  extensions. Finds deeper paths, backup files, and uncommon admin panels.

## Scenario 9: Dirbuster medium wordlist (largest built-in)
Method: dir_fuzz
Args: {url: "http://<IP>/FUZZ", wordlist: "dirbuster-medium", threads: 50}
Expected: success=true, most comprehensive scan
Notes: 220,546 entries. No real engagement used this yet, but it is the nuclear
  option when common and big both miss. Takes 30+ minutes without extensions.
  Increasing threads to 50 helps but may trigger rate limiting on some targets.

## Scenario 10: Raft wordlist (different word source)
Method: dir_fuzz
Args: {url: "http://<IP>/FUZZ", wordlist: "raft-small"}
Expected: success=true, results from raft-curated word list
Notes: 1 real call used "raft-small-words" (which resolved to common fallback
  because the WORDLISTS dict uses "raft-small" not "raft-small-words"). Tests
  wordlist name resolution and fallback behavior.

## Scenario 11: Non-existent wordlist name (fallback behavior)
Method: dir_fuzz
Args: {url: "http://<IP>/FUZZ", wordlist: "raft-small-words"}
Expected: success=true, falls back to common wordlist (with warning in logs)
Notes: Real call from Pirate HTB. The wordlist name "raft-small-words" is NOT
  in the WORDLISTS dict (correct name is "raft-small"). _resolve_wordlist() falls
  back to common. Agent gets correct results but may not realize the wordlist
  changed. Tests the silent fallback behavior.

## Scenario 12: Custom wordlist path
Method: dir_fuzz
Args: {url: "http://<IP>/FUZZ", wordlist: "/session/wordlists/custom.txt"}
Expected: success=true if file exists, error if not
Notes: Agent used custom wordlist paths in param_fuzz engagements. When wordlist
  is not a known name, _resolve_wordlist() returns it as-is (assumes path).
  The /session/ directory maps to the session working directory in the container.

## Scenario 13: Status code filtering (filter out 403/404)
Method: dir_fuzz
Args: {url: "http://<IP>/FUZZ", wordlist: "common", filter_codes: "404,403"}
Expected: success=true, results exclude 404/403 responses
Notes: Removes noise from forbidden directories and not-found pages. The default
  match_status already includes 403, so filter_codes overrides the default match
  to further remove unwanted codes. Common for IIS targets that return 403 for
  every directory.

## Scenario 14: Match status whitelist (200 and 301 only)
Method: dir_fuzz
Args: {url: "http://<IP>/FUZZ", wordlist: "common", match_status: "200,301"}
Expected: success=true, only 200 and 301 results shown
Notes: Whitelist approach. Tighter than the default (200,204,301,302,307,401,403,405).
  Useful when you only want actual content (200) and redirects (301). Eliminates
  401/403 noise on locked-down targets.

## Scenario 15: Match status with 401 included (auth-required endpoints)
Method: dir_fuzz
Args: {url: "http://<IP>/FUZZ", wordlist: "common", match_status: "200,301,302,401"}
Expected: success=true, shows endpoints requiring authentication
Notes: Including 401 reveals protected endpoints that exist but need credentials.
  Good for mapping attack surface before credential testing.

## Scenario 16: Auto-calibrate filtering (recommended default)
Method: dir_fuzz
Args: {url: "http://<IP>/FUZZ", wordlist: "common", auto_calibrate: true}
Expected: success=true, automatically filters default responses
Notes: ffuf's -ac flag sends random strings first, measures the baseline response,
  then filters results matching that baseline. Most effective single setting for
  eliminating false positives. 1 real call used auto_calibrate with dir_fuzz,
  more with vhost_fuzz where it is critical.

## Scenario 17: Size-based filtering
Method: dir_fuzz
Args: {url: "http://<IP>/FUZZ", wordlist: "common", filter_size: "277"}
Expected: success=true, responses of size 277 are excluded
Notes: Real pattern: filter the known "not found" page size. Workflow: (1) curl
  a non-existent path, note Content-Length, (2) use that as filter_size. The value
  "277" is a real default 404 page size from engagement data. Multiple size values
  can be comma-separated: filter_size: "273,274,276,277".

## Scenario 18: Multiple size filtering (range of default pages)
Method: dir_fuzz
Args: {url: "http://<IP>/FUZZ", wordlist: "common", filter_size: "273,274,276,277"}
Expected: success=true, all four sizes filtered out
Notes: Real pattern from tunnel target engagement. Some servers return slightly
  different sizes for the same 404 page due to path echoing in the response body.
  Comma-separated filter_size handles this variation.

## Scenario 19: Word count filtering
Method: dir_fuzz
Args: {url: "http://<IP>/FUZZ", wordlist: "common", filter_words: "42"}
Expected: success=true, responses with 42 words are excluded
Notes: Alternative to size filtering when pages have dynamic elements that change
  size but consistent word count. Also handles: "10-50" (range), "0" (empty).

## Scenario 20: Line count filtering
Method: dir_fuzz
Args: {url: "http://<IP>/FUZZ", wordlist: "common", filter_lines: "0"}
Expected: success=true, empty responses filtered out
Notes: filter_lines: "0" removes empty responses. Useful when target returns
  200 OK with empty body for non-existent paths (instead of proper 404).

## Scenario 21: Combined filters (auto-calibrate + status filter)
Method: dir_fuzz
Args: {url: "http://<IP>/FUZZ", wordlist: "common", auto_calibrate: true, filter_codes: "403"}
Expected: success=true, both auto-calibrate and 403 filter applied
Notes: Real pattern from WinRM engagement (10.129.231.186:5985). Combining
  auto_calibrate with explicit filters gives most precise results. The auto_calibrate
  handles unknown baseline, filter_codes removes known-unwanted status codes.

## Scenario 22: Combined match + filter (whitelist with exclusions)
Method: dir_fuzz
Args: {url: "http://<IP>/FUZZ", wordlist: "common", match_status: "200,301,302,401", filter_size: "0"}
Expected: success=true, only matched statuses minus empty responses
Notes: Advanced filtering: whitelist interesting codes, then exclude empties.
  match_status and filter_codes/filter_size are not mutually exclusive in ffuf.

# HEARTBEAT AND TIMEOUT BEHAVIOR SCENARIOS
# ===============================================================================
#
# The 71.4% timeout rate on dir_fuzz was caused by the MCP client killing idle
# connections after 300s with no output. Fixed by adding heartbeat support via
# run_command_with_progress() with heartbeat_interval=15s. Post-fix timeout rate

## Scenario 57: Invalid param name ("filter_status" - most common LLM mistake)
Method: dir_fuzz
Args: {url: "http://<IP>/FUZZ", wordlist: "common", filter_status: "200,204,301,302,307,401,403,405"}
Expected: success=true, BUT filter_status is silently ignored (no filtering applied)
Notes: "filter_status" was used 8 times across real engagements. It is NOT a valid
  parameter. The server ignores unknown params, so the agent gets unfiltered results
  without any error. This is a silent failure. The correct params are:
  - match_status: whitelist codes to SHOW
  - filter_codes: blacklist codes to HIDE
  Scenario validates the silent ignore behavior. Consider adding server-side
  validation for unknown params in a future update.
